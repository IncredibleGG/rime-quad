# 風格、方案、詞庫:三件事,不要混

| | |
|---|---|
| 狀態 | **已決定,四端共用。** 這一輪只寫規範與盤點,**沒有動任何程式碼** |
| 維護者 | 誰先實作誰補,**只加不刪別人的段落** |
| 管什麼 | 這三個概念的**邊界**:哪個設定屬於哪一個、哪些組合合法、不合法時使用者看到什麼 |
| **不管**什麼 | 每個欄位的型別與預設(那是 `docs/theme-format.md` 與 `docs/settings-model.md`)、畫成什麼樣子(那是 `docs/ui-design.md`) |

使用者的原話(2026-08-09):

> **「風格、詞庫、方案,不相關對不?所以你不要給他們混為一談。這一塊好好熟悉下。」**

**他是對的,而我們現在混在一起了。** 四條證據,每一條都讀過碼:

1. `core/layouts/` 裡三份九宮格佈局(`cn-t9-pinyin`、`cn-t9-pinyin-numrow`、`t9-pinyin`)
   全部寫著 `for_schema: ["t9_pinyin"]` —— 於是「九宮格」在使用者眼中不是一種鍵盤長相,
   而是一個方案。
2. `core/layouts/cn-qwerty-numrow.yaml` 寫著 `for_schema: ["luna_pinyin"]`(**只掛原版,
   不掛預設的 `luna_pinyin_tw`**)。後果:**使用者想要「鍵盤上多一列數字」這個純外觀的東西,
   得先把方案從「臺灣正體」換成「原版朙月拼音」** —— 而那會改變他打出來的字。
   那個檔案自己寫著「`for_schema` 就是把兩者綁在一起的欄位,這裡是它的第一個真實用例」。
3. Android 首頁「打字方式」那一列的現值是 `%1$s · %2$s` = **佈局名 · 方案名**
   (`home/KeyboardChoice.kt:269`),而 `cn-t9-pinyin-numrow` 的佈局名本身叫
   「九宮格拼音・數字列」、方案名也叫「九宮格拼音」。使用者看到的是
   **「九宮格拼音・數字列 · 九宮格拼音」**。
4. 拼音消歧欄的位置寫死在 Kotlin 裡(`android/.../keyboard/T9Syllables.kt` 的 `SLOTS`,
   白名單兩個佈局 id + 寫死的 layer id `"t9"` + 寫死的三個 key id)。
   那份檔案自己承認「**這份宣告本該住在佈局 YAML 裡**」。

於是「我想用九宮格 + 繁體輸出 + 我自己的詞庫」這種再正常不過的組合,現在做不到。
第 §2.4 節逐項回答為什麼。

## 1. 三條邊界

### 1.1 用使用者的語言定義

| | 使用者腦中那句話 | 我們的東西 |
|---|---|---|
| **風格** | 「鍵盤長什麼樣」 | `core/themes/*.yaml` + `core/layouts/*.yaml` + 換鍵檔 |
| **方案** | 「怎麼把我按的鍵變成字」 | RIME 的 schema(`*.schema.yaml`) |
| **詞庫** | 「它認得哪些詞、學過我什麼」 | 內建詞典 + 使用者自己造的詞 + librime 學到的詞 |

**三句話各自的完整版:**

* **風格** = 眼睛看得到、**換掉之後打出來的字完全一樣**的一切。
  鍵盤幾個鍵、鍵面印什麼、顏色字級圓角、鍵盤多高、候選列是橫是直、消歧欄擺哪裡。
* **方案** = 同樣按下去、**換掉之後會出現不同的字**的一切。
  拼音/注音/九宮格/倉頡、簡繁、標點全半形、一頁幾個候選、選字鍵。
* **詞庫** = **重灌之後會不見、而使用者會心痛**的一切。
  他自己加的「黃小明」、系統學會的「我常打這個」。

### 1.2 歸屬表(規範性)

### 1.3 下次有新設定時,照這三個問題判

1. **「換一個主題,這件事會不會變?」** 會 → **風格**。
2. **「同一串按鍵,換一個方案會不會打出不同的字?」** 會 → **方案**。
3. **「重灌之後這件事會不會不見,而使用者會心痛?」** 會 → **詞庫**。

三個都答「不會」的東西,通常根本不該是設定項。

### 1.4 幾條會被吵的邊界,直接把理由寫死

**⚠ 簡繁屬於「方案」,不屬於「風格」。**
它改變的是**上屏的字**,不是畫面。放進「外觀」頁是錯的。
`docs/settings-model.md` §4 已經規範了輸入模式↔方案↔簡繁的關係,那一節仍然有效;
但它的 §4.5 有一條**現在已知是不夠的**規則,見 §6.4。

**⚠ 「一頁幾個候選」屬於「方案」,即使它畫在「外觀」頁上。**
它是 librime 的 `menu/page_size`,是 A 層設定,**改了要重新部署**。
`docs/theme-format.md` §8.6.7.1 已明訂主題**不得**改變它。
理由不是潔癖:**只改畫面的話,使用者按數字鍵仍然會選到看不見的那幾個。**
Windows 端的介面文案已經把這句話寫出來給使用者看了,那是對的做法。
> **它畫在哪一頁不改變它屬於誰。** UI 分頁照的是使用者的心智,歸屬照的是機制。
> 兩者不一致時,**要在畫面上說出來**(「改這一項要重新整理字詞才會生效」),不是偷偷處理掉。

**⚠ 選字鍵屬於「方案」,但「序號標籤顯不顯示」屬於「風格」,而且兩者有耦合。**
選字用哪幾顆鍵是 librime 的事(`select_labels` > `menu.select_keys` > 序號,
見 `core/include/rime_shell.h`);標籤畫不畫是主題的事。
**耦合:方案還在用數字選字、主題卻把標籤藏起來 → 使用者沒有辦法知道按 3 會選到哪一個。**
規則:**`showLabels` 為 off 時,實作必須同時確認該方案沒有在用鍵盤選字**;
用了就忽略 off 並產生一則 INFO 診斷。這與 §8.6.6.1 的「必備項」是同一種保護。

**⚠ 中英切換是兩件事各一半,不是一件事。**
引擎那一半是方案(`ascii_mode`),鍵盤那一半是風格(`alpha_layer` 換層)。
`docs/theme-format.md` §9.1.2 已經規範,並記著只做引擎那一半的後果:
「使用者進了英文模式,眼前仍然是 abc/def/ghi 八顆鍵,26 個字母一個都打不出來」。

**⚠ 詞庫是三者裡唯一「使用者做的功」。** 風格和方案壞了重設就好,詞庫壞了是資料損失。
所以任何會清掉詞庫的操作都適用 `docs/ui-design.md` §4.9 的危險操作規則,
而「全部回復預設」**不得**碰它。

## 2. 誠實面對:它們在引擎層不是完全正交

**上面那張表是我們對使用者的承諾。它在引擎層並不是免費的。**
這一節寫清楚代價在哪裡,以及哪些是物理限制、哪些只是我們沒做。

### 2.1 佈局 ↔ 方案:兩個測試,一個機器驗得了,一個驗不了

一份佈局能不能配一個方案,取決於兩件事:

> **T1(可運作性,機器驗得了):**
> 佈局在**主層**送出的 keysym 集合,必須落在方案的 `speller/alphabet` 裡。
> 兩邊都是宣告好的資料,這條可以寫成一支 CI 檢查。
>
> **T2(誠實性,機器驗不了):**
> **鍵面印的東西,必須與按下去真的會發生的事對得上。**
> 這需要語義知識,格式檢查不到。**這就是 `for_schema` 必須由作者宣告、
> 不能從 `kind` 或 `inherits` 推論的理由**(§9.1.1 已經記過兩層失敗的推論)。

實測資料(全部讀自 repo,見 §7):

| 方案 | `speller/alphabet` |
|---|---|
| `luna_pinyin` / `luna_pinyin_tw` | `zyxwvutsrqponmlkjihgfedcba`(小寫 a–z) |
| `bopomofo` / `bopomofo_tw` | `1qaz2wsxedcrfv5tgbyhnujm8ik,9ol.0p;/- 6347` |
| `stroke` | `abcdefghijklmnopqrstuvwxyz` |
| `t9_pinyin` | `ADGJMPTW`(**八個大寫字母,刻意不含 0–9**) |

套上兩個測試:

| 佈局 | 方案 | T1 | T2 | 判定 |
|---|---|---|---|---|
| `cn-t9-pinyin`(送 A/D/G/J/M/P/T/W) | `t9_pinyin` | ✅ | ✅ 鍵面 `abc`、角標 `2`、送 `A` | **合法** |
| `cn-t9-pinyin` | `luna_pinyin` | ❌ 大寫 `A` 不在 `a–z` 裡 | ❌ | **物理上不可能** |
| `qwerty`(送 a–z) | `luna_pinyin` | ✅ | ✅ | **合法** |
| `qwerty` | `t9_pinyin` | ❌ `a` 不在 `ADGJMPTW` 裡 | ❌ | **物理上不可能** |
| `bopomofo-dachen` | `bopomofo_tw` | ✅(鍵面 ㄅ、送 keysym `1`) | ✅ | **合法** |
| `qwerty` | `bopomofo_tw` | ✅ 26 個字母全在那串裡 | ❌ **鍵面印 `a`,打出來是 ㄇ** | **桌面是慣例,行動端不可接受** |
| `cn-stroke`(送 h/s/p/n/z) | `luna_pinyin` | ✅ h,s,p,n,z ⊆ a–z | ❌ 五顆筆畫鍵打不出拼音 | ⚠ **最惡劣的一種:按鍵「有反應」,就是打不出字** |

⚠ **最後兩列是這一節的重點。** T1 過了不代表能用。
所以 **T1 只能當下界**(用來抓「連字都送不進去」的宣告錯誤),
**不能**拿來自動產生 `for_schema`。

**建議的 CI 檢查(給 Android 端,`core/layouts/` 的擁有者):**
對每一份佈局的每一個 `for_schema` 條目,驗 T1;不過就是紅的。
它今天抓不到任何東西(現有宣告都是對的),但它會擋住下一次有人隨手寫 `["*"]`。
⚠ **這支檢查必須先植入一個違規、確認它真的會紅**(`docs/coordination.md` §3 的紀律)。

**現況:`for_schema` 只是建議,不是門閂。**
`android/.../keyboard/LayoutHost.kt` 的 `applySchema()` 第 0 步是「使用者釘過的佈局優先」,
**排在任何 `for_schema` 檢查之前**。所以使用者可以把 `bopomofo-dachen` 釘到 `luna_pinyin` 上,
得到一個渲染完美、一個字也打不出來的鍵盤。**這一條要修**,見 §3.2。

### 2.2 詞庫 ↔ 方案:編碼欄是「按鍵」,所以詞庫綁在方案上

⚠⚠ **這是三者裡最違反直覺的一條,而且它已經害我們下架過一頁。**

`docs/settings-model.md` §5.2(已用真的 librime 驗過)寫著:
`custom_phrase.txt` 的第二欄 = **使用者實際按的那一串鍵,原樣**,不是音節。
同一個詞「你好」,在三個方案底下是三個不同的編碼:

| 方案 | 使用者按的 | 檔案裡要寫 |
|---|---|---|
| `luna_pinyin` | n i h a o | `nihao` |
| `t9_pinyin`(九宮格) | mno · ghi · ghi · abc · mno | `mggam` |
| `bopomofo_tw` | 大千鍵位 | `su3cl3` |

而 `custom_phrase.txt` **只有一份,而且掛在每一個已啟用的方案底下**
(`docs/settings-model.md` §5.3)。後果:

* 使用者在拼音底下加的「黃小明」,**在九宮格底下叫不出來** —— 因為他永遠按不出 `huangxiaoming`。
* 它不會出錯、不會有訊息。詞條載入了,只是查不到。**這正是 §3 要防的那一類失敗。**
* 反向也成立但無害:`mggam` 在拼音底下仍然查得到(那是一串合法的拼音輸入),
  只是沒有人會去按它。

**所以:詞庫「是第三件獨立的事」這句話,今天只對「詞」那一半成立,對「編碼」那一半不成立。**

**要讓它真的獨立,只有一條路:替使用者把編碼推導出來。**
「黃小明」→ 逐字查讀音 → 套上目標方案的 `speller/algebra` → 得到該方案的按鍵串。
拼音家族的 `.dict.yaml` 有單字讀音,推得出來;多音字會產生多筆(那沒關係,多寫幾行就好)。
**這是實作工作,不是格式限制。** 在做完之前,**介面必須誠實**,見 §3.2 的 D 案。

⚠ **不要用「加一個第四欄記方案」來解。** librime 讀 TSV 時不會依欄位過濾。
真要分方案,正確的形態是**分檔** —— `custom_phrase/user_dict: custom_phrase_<schema>`,
每個方案掛自己那一份。這是 RIME 原生支援的。**但那要 dict 支線裁決**(它是 `backup-format.md`
與 `settings-model.md` §5 的擁有者),本文件只指出問題,不改格式。

### 2.3 消歧欄 ↔ 方案:沒有 `spelling_hints` 就沒有東西可列

消歧欄要列的是「這幾下按鍵可能是哪些音節」。這個資訊來自 librime 的
`translator/spelling_hints`,它把完整拼寫掛進候選的 `comment` 欄
(`core/include/rime_shell.h:223`)。

**隨附的方案裡只有 `t9_pinyin` 宣告了 `spelling_hints: 5`。**
(`terra_pinyin` 也有,但它沒有進 `schema_list`,只是 `bopomofo*` 的詞庫來源。)

**但這不是缺口,是正確的。** 消歧欄要解的問題是「一顆鍵三四個字母」造成的模糊,
全拼、注音、筆畫**沒有這個模糊**,那裡本來就沒有東西可消。
規則:**方案給不出音節時,消歧欄整條不出現**(不是空的一條,見 §5.2)。

### 2.4 所以「九宮格 + 繁體 + 我自己的詞」到底能不能?

逐項回答。

| 要的東西 | 今天 | 說明 |
|---|---|---|
| **九宮格** | ✅ **只有 Android** | `cn-t9-pinyin`(5 欄華語慣例版)已上線。桌面兩端沒有軟鍵盤,**刻意不打包 `core/layouts/`**;iOS 端不存在 |
| **繁體輸出** | ✅ | `t9_pinyin` 的詞典就是 `luna_pinyin.dict.yaml`,**本來就是繁體**;它的字形選項組預設落在第 0 項「傳統漢字」。**不必做任何事就是繁體** |
| **我自己的詞** | ❌ | 見下 |

**「我自己的詞」為什麼是 ❌,有兩層,兩層都要說:**

1. **Android 根本沒有加詞的介面。** 唯一有的是 macOS 的「自己加的詞」那一頁。
   Android 這一側只有備份路徑碰得到 `*.userdb/`(`store/UserDbSnapshot.kt`),
   沒有 `custom_phrase.txt` 的讀寫。→ **這是「還沒做」。**
2. **就算接了 UI,§2.2 的編碼問題還在。** 使用者在拼音底下加的詞,切到九宮格叫不出來。
   → **這是「機制問題」,補一頁 UI 解決不了。**

⚠ **還有一個會咬人的交互作用:** Android 的簡繁選擇是**全域**的
(`RimeInputMethodService.applyVariant()`,DataStore 鍵 `opt_simplification`),
而且**每次換方案都會被重新推一次**到新的 session 上。
所以「我在拼音那邊選過簡體」→ 切到九宮格 → **九宮格也變簡體**,
即使那個選擇跟九宮格一點關係都沒有。
而記住「原本是哪一種字形」的 `savedVariantOption` 是 service 上的**單一欄位**,
不是 per-schema —— 換方案時可能還原到錯的那一個。

**結論(要給使用者看的版本):**
> 九宮格 + 繁體,今天在 Android 上就是預設的行為,不必設定。
> 「我自己的詞」今天做不到,而且它做不到的原因不是少一頁畫面。

### 2.5 哪些組合真的不可能,哪些只是我們沒做

| 組合 | 判定 | 理由 |
|---|---|---|
| 九宮格佈局 + `luna_pinyin` / `bopomofo` / `stroke` | 🚫 **物理上不可能** | T1 不過。`Engine::ProcessKey` 一次只吃一個 keycode,「一鍵三字母」的模糊只能由 speller 的 algebra 與 prism 承擔,**前端無從介入** |
| 九宮格 + **任何**拼音方案的繁/簡變體 | ⚙ **只是沒做** | 要為每個變體打包(或衍生)一份 T9 方案。見 §2.6 |
| 九宮格 + 倉頡 / 五筆 | 🚫 **可做但沒意義** | 折成八鍵之後重碼會爆炸,而形碼使用者選形碼正是為了低重碼。**不要做** |
| 九宮格 + 注音 | ⚙ 只是沒做,但要另設計 | 注音本來就有自己的九宮格慣例(不是 ABC 分組),那是一份新佈局 + 一份新方案,不是衍生 |
| 全鍵盤 + 數字列 + `luna_pinyin_tw` | ⚙ **只是沒做,而且是一行的事** | `cn-qwerty-numrow.yaml` 的 `for_schema` 加一個 id 就好。今天沒加,於是使用者得換方案 —— **這是本文件證據 #2** |
| 任何佈局 + 任何方案,只要 T1 過 | ⚠ 技術上可配 | 但 T2 要人判斷。**不得**自動放行 |
| 同一份使用者詞庫跨方案生效 | ⚙ **只是沒做**(要推導編碼,見 §2.2) | 不是格式限制 |
| 桌面端選佈局 | 🚫 **不存在這個概念** | 桌面沒有軟鍵盤。`docs/theme-format.md` §9 明訂桌面端**必須**完全不讀 `core/layouts/` |

### 2.6 做得到的部分要怎麼接

三條路線,推薦第一與第二並用:

**路線 A —— 打包 T9 變體(現況,推薦給內建方案)。**
為要支援九宮格的方案各打包一份 `<schema>_t9`。
`t9_pinyin` 就是這麼做的:共用 `luna_pinyin.dict.yaml`,只多編一份 prism。
成本低、行為可預期、CI 驗得到。
⚠ **必須另取 prism 名**(`prism: t9_pinyin`)—— 拼寫規則不同的兩個方案共用 prism 會互相覆蓋,
`t9_pinyin.schema.yaml` 的檔頭已經寫過這一條。

**路線 B —— 執行期衍生(推薦給市集方案)。**
用 `<schema>.custom.yaml` 的 patch 換掉 `speller/alphabet`、`speller/algebra`、`translator/prism`。
內容就是 `t9_pinyin.schema.yaml` 現在內嵌的那幾行。
衍生前**必須**預檢三件事,任何一項不過就不提供九宮格:
1. 方案的 `speller/alphabet` 是 a–z 的子集(折疊規則只對拉丁字母成立);
2. 有 `enable_sentence`(或我們補上)—— 折疊後重碼極多,逐字選不能用;
3. 有語言模型(`grammar:/hant?` → rime-essay)—— 沒有的話候選排序會爛到使用者以為壞了。

⚠ **路線 B 會與「自己加的詞」搶同一個檔案。** `<schema>.custom.yaml` 現在已經被
使用者詞庫的掛載寫入(`docs/settings-model.md` §5.3,dictfix 支線)。
兩邊都要照那一節的 `# luminakey-managed:` 標記做**外科手術式**的合併,不可重寫整份。
⚠ 另外要注意:`SchemaPreflight` 對這個檔案的存在與否敏感(coordination §5 的 2026-08-09 條目已記)。

**路線 C —— 用 `key_binder` 繞。🚫 不可行,而且要明確關掉。**
`key_binder` 是 keysym → keysym 的替換,**它造不出「一顆鍵對應多個音節」的模糊性**。
模糊只能由 prism 承擔。`core/layouts/t9-pinyin.yaml` 的檔頭已經把這條路走過一次並寫下結論。
**寫在這裡是為了不要有人再試第二次。**

## 3. 使用者選了一個做不到的組合時,要看到什麼

⚠ **這一節是硬規則。這個專案已經抓過六次「畫面正常、自動化全過、按了沒反應」的缺陷**
(重輸鍵、中英鍵、按下後顏色回不來、工具列 emoji 鍵、退格、診斷捷徑)。
**不合法組合的處置,不可以再變成第七次。**

### 3.1 ⛔ 三種絕對禁止的處置

1. **⛔ 安靜地不生效。** 使用者選了、設定值也存下來了、畫面上打了勾,行為沒變。
   *(今天真的存在:macOS 的「外觀」頁六個控制項就是這樣 —— 見 §6.3。)*
2. **⛔ 灰掉但不說為什麼。** 灰色控制項沒有解釋 = 使用者以為是自己做錯了。
3. **⛔ 讓他選到「畫得出來但打不出字」的組合。**
   *(今天真的存在:釘一份 `for_schema` 不符的佈局,以及 macOS 上的 `t9_pinyin` —— 見 §6.3。)*

### 3.2 四級處置(規範性)

| 級 | 做法 | 用在哪 |
|---|---|---|
| **L0** | **不出現在選單裡** | `for_schema` 不含當前方案的佈局。**但必須配 L3**,否則使用者會問「九宮格跑哪去了」 |
| **L1** | **出現、可選,選了會連帶改別的** —— 動作前先說清楚,由使用者按下確認 | 使用者要九宮格而當前方案不支援 → 同時換方案 |
| **L2** | **出現、可選,選了被擋下** —— 說出缺什麼 + 一顆按得下去的按鈕 | 衍生預檢不過、缺語言模型、缺檔 |
| **L3** | **不出現,但選單底部固定一行說明** | 常駐一句「有些鍵盤只有特定的打字方式才能用」+ 可展開清單 |

**逐案指派:**

| 案 | 情境 | 級 | 使用者看到 |
|---|---|---|---|
| A | 當前方案是拼音,使用者想要九宮格 | **L1** | 見下方對話框 |
| B | 使用者釘的佈局對新方案不合法 | **L1**(不是安靜換掉) | 「你為『注音』選過『大千』。『拼音』用不了它,已經換回全鍵盤。」+ 一顆「改回去」 |
| C | 方案沒有 `spelling_hints`,主題卻要消歧欄 | **L0** | 整條不出現,`syllables:toggle` 那顆鍵**跟著隱藏**(不是變灰) |
| D | 使用者在 A 方案加的詞,切到 B 方案 | **L3 + 標記** | 詞的清單上每一筆標「拼音」;頁面頂端一句「你加的詞跟著打字方式走」 |
| E | 市集方案衍生不出 T9 | **L2** | 「『○○』沒辦法做成九宮格,因為它不是用字母拼的。」 |
| F | 桌面端使用者看到 `t9_pinyin` | **L0** | **桌面端根本不該列出它**。見 §6.3 |

**A 案的對話框(規範性文案,四端共用):**

```
┌──────────────────────────────────────────┐
│  要換成九宮格,打字方式也要一起換     t3  │
│                                          │
│  九宮格是一顆鍵三四個字母,只有       t5  │
│  「九宮格拼音」認得這種按法。            │
│  你現在用的是「拼音・臺灣正體」。        │
│                                          │
│  換過去之後:                             │
│   ✓ 一樣打繁體字                         │
│   ⚠ 你自己加的詞要重新加一次             │
│                                          │
│      [ 算了 ]      [ 換成九宮格 ]        │
└──────────────────────────────────────────┘
```

⚠ 那一行「你自己加的詞要重新加一次」**是 §2.2 的直接後果**。
它很難看,但它是真的。**§2.2 的推導做完之後,這一行要拿掉,不是提早拿掉。**

### 3.3 一條給所有實作的驗收問句

> **「使用者按下去之後,畫面上有沒有任何一個像素改變?」**
> 沒有 → 這就是第七個缺陷,不要交出去。

## 4. 設定介面該長什麼樣

### 4.1 三個獨立的選擇,不等於三個技術名詞

使用者是全世界的麻瓜(`docs/ui-design.md` §6)。三個問題在畫面上的說法:

| 概念 | 畫面上叫 | ⛔ 不准出現 |
|---|---|---|
| 方案 | **「打字方式」** | 方案、schema、schema_id、輸入法引擎 |
| 風格(佈局) | **「鍵盤形狀」** | 佈局、layout、for_schema |
| 風格(其餘) | **「外觀」** | 主題、theme、palette |
| 詞庫 | **「自己加的詞」** / **「學過的字」** | 詞典、詞庫、userdb、部署 |

⚠ **現況有三個名字指同一件事:** Android 的 App 頁叫「打字方式」、鍵盤上的面板叫「鍵盤類型」、
還有一個沒在用的字串 `page_keyboard` =「鍵盤」;而「下載更多鍵盤」裡的「鍵盤」其實是方案,
「跟著鍵盤」裡的「鍵盤」其實是方案的預設。**四個指涉,一個詞。** 這一條要收斂。

### 4.2 行動端:一頁,兩段,不是一個扁平清單

⚠ **不要把佈局搬到「外觀」頁。**
使用者心裡「我要用九宮格」是一個**打字方式**的決定,不是一個**外觀**的決定。
Android 端當初把兩者攤平(照三星的鍵盤類型選單)**方向是對的** ——
錯的是攤平之後**看不出哪一個是哪一個**,而且只要碰任何一項就整組重來(§6.2)。

**正確的形態是同一頁上的兩段:**

```
┌──────────────────────────────────────────┐
│  ‹ 返回   打字方式                   t2  │
│                                          │ ← s5
│  用哪一種                            t5  │ ← 第一段:方案
│  ┌────────────────────────────────────┐  │
│  │ ◉ 注音 · 臺灣正體                  │  │
│  │   大千排列,和市面上的注音一樣  t5  │  │
│  ├────────────────────────────────────┤  │
│  │ ○ 拼音 · 臺灣正體                  │  │
│  │   漢語拼音,打出來是繁體字      t5  │  │
│  ├────────────────────────────────────┤  │
│  │ ○ 九宮格拼音                       │  │
│  │   像老手機那樣,一顆鍵三個字母  t5  │  │
│  └────────────────────────────────────┘  │
│                                          │ ← s7
│  鍵盤長什麼樣                        t5  │ ← 第二段:佈局
│  只列出「注音 · 臺灣正體」用得上的。 t5  │ ← ⚠ 這一句是 L3
│  ┌──────────┬──────────┐                 │
│  │  大千    │ 全鍵盤   │                 │ ← 分段控制,不是清單
│  └──────────┴──────────┘                 │
│                                          │ ← s7
│  ┌────────────────────────────────────┐  │
│  │ 換鍵                             ›  │  │
│  ├────────────────────────────────────┤  │
│  │ 下載更多打字方式  需要連上網路  ›  │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

**規範性的部分:**

1. **兩段有各自的標題**,而且第二段的說明句要點名第一段的現值
   (「只列出『注音 · 臺灣正體』用得上的」)。這一句同時完成 L3 —— 使用者
   不必猜為什麼九宮格不在這裡。
2. **第二段只有一個選項時,整段不畫**(不要畫一個只有一格的分段控制)。
   ⚠ 但 L3 那一句仍然要在,否則「為什麼沒得選」變成一個謎。
3. **只動第二段的時候,不得重新選方案。** 這是 §6.2 的 Android bug。
4. **首頁那一列的現值改成「方案 · 佈局」,方案在前**
   (`docs/ui-design.md` §7.1 的草圖本來就是這樣寫的:「注音 · 大千排列」)。
   現在是「佈局 · 方案」,而且兩邊都可能叫「九宮格拼音」。

⚠ **佈局的顯示名要改,而且要 Android 端動 `core/layouts/`:**

| 檔案 | 現在 | 建議 | 為什麼 |
|---|---|---|---|
| `cn-t9-pinyin` | 九宮格拼音 | **九宮格** | 「拼音」由方案那一段說,佈局不必再說一次 |
| `t9-pinyin` | 九宮格拼音 | **九宮格(4 欄・舊版)** | ⚠ **它與上一列現在是同一個名字**,選單上會出現兩筆一模一樣的 |
| `cn-t9-pinyin-numrow` | 九宮格拼音・數字列 | **九宮格 + 數字列** | 名字裡的 `・` 與「方案 · 佈局」的分隔號打架 |
| `cn-qwerty-numrow` | 全鍵盤・數字列 | **全鍵盤 + 數字列** | 同上 |

### 4.3 桌面端:沒有第二段,因為桌面沒有軟鍵盤

側欄維持 `docs/settings-model.md` §1 的八頁。「輸入方案」頁**只有方案**。

⚠ **桌面端不得長出「鍵盤形狀」。** `docs/theme-format.md` §9 明訂桌面端
**必須**完全不讀 `core/layouts/`,兩個桌面端今天也都沒讀(已讀碼確認)。
桌面上與「鍵盤」有關的唯一設定是**換鍵**,而那是 `docs/settings-model.md` §7 規範過的另一件事
(桌面換的是 keysym,行動端換的是鍵的位置 —— **不要合成一項**)。

**桌面端要改的兩件事:**

1. **「一次顯示幾個字」畫在「外觀」頁,但它是方案設定。**
   保留位置(使用者的心智就是外觀),但**必須**帶那句「改這一項要重新整理字詞才會生效」。
   Windows 端的文案已經是對的,macOS 端要跟上。
2. **「配色」的清單不得列出行動端的鍵盤主題。**
   macOS 現在把 `core/themes/*.yaml` 全部列出來,包含 `intl-gboard` / `intl-ios` /
   `intl-samsung` / `cn-compact` —— 那些主題的重點是 `keyboard:` 區塊,而桌面端整段忽略。
   而且它顯示的是**原始 id**,不是 `name`。

### 4.4 iOS(尚不存在,但規範先寫下來)

iOS 端一行程式碼都還沒有。它落地時**必須**與 Android 用同一份 `core/layouts/`
與同一套 §4.2 的兩段式版面。⚠ `docs/theme-format.md` §2.3 已經寫著
iOS 的主題目錄**必須**在 App Group 容器內,否則主 App 寫的主題鍵盤擴充看不到。

## 5. 消歧欄的位置屬於「風格」

### 5.1 三家的做法都不一樣,所以它一定是宣告出來的

| | 消歧欄在哪 | 怎麼叫出來 |
|---|---|---|
| **三星** | **左側直欄** | 一開始打字就自動出現 |
| **語燕** | **左側直欄**(取代標點欄) | 一開始打字就自動出現。內容 `mi / ni / m / n / o` |
| **iOS 九宮格** | **候選列上方一橫排** | 底列有一顆專門的「选拼音」鍵 |

我們兩家的風格都支援(`core/themes/intl-samsung-*`、`core/themes/intl-ios-*`)。

> **同一個功能、同一個方案、同一份詞庫,位置卻不同 —— 那就是風格的定義。**
> 位置**不得**寫死在程式碼裡。

### 5.2 現況:它寫死在 Kotlin 裡,而且原始碼自己承認

`android/app/src/main/java/org/luminakey/ime/keyboard/T9Syllables.kt`:

```kotlin
val SLOTS: Map<String, SlotSpec> = mapOf(
    "cn-t9-pinyin"        to SlotSpec("t9", listOf("pu_comma", "pu_period", "pu_question")),
    "cn-t9-pinyin-numrow" to SlotSpec("t9", listOf("pu_comma", "pu_period", "pu_question")),
)
```

寫死了**佈局 id 白名單**、**layer id `"t9"`**、**三個 key id**。該檔案的檔頭寫著:

> ── ⚠ 這份宣告**本該住在佈局 YAML 裡** ──
> 正確的形態是在 `core/layouts` 底下那幾份 yaml 的 layer 上加一個 `syllable_slots:`……
> 那是**格式擴充**,照 `docs/coordination.md` §2 只能回報、不能自己加。

`core/layouts/cn-t9-pinyin.yaml` 的註解也寫了同一件事,並指出後果:
**「否則有人改個 key id,消歧欄會整欄靜靜消失而畫面看起來完全正常。」**

⚠ **兩份主題(`intl-ios-*`)配的是 `intl-ios.yaml`,而那是一份 `kind: alphabetic`、
`for_schema: ["*"]` 的 QWERTY 佈局 —— 不是九宮格。**
也就是說:我們有 iOS 的**外觀**,沒有 iOS 的**九宮格佈局**。
使用者給的那張截圖對應的東西,今天在 repo 裡不存在。**這一條要照實說,不要當成已支援。**

### 5.3 規範:誰宣告什麼

| 誰 | 宣告什麼 |
|---|---|
| **方案** | 有沒有東西可列(`translator/spelling_hints`) |
| **主題** | **擺在哪裡**、長什麼樣、什麼時候出現 |
| **佈局** | 哪一欄/哪幾格可以讓出來、有沒有「选拼音」那顆鍵 |
| **程式碼** | 以上三者都沒宣告的東西,**一律不得自己決定** |

### 5.4 `docs/theme-format.md` 要補什麼(給 macOS 端)

⚠ **`docs/theme-format.md` 只有 macOS 端能改**(`docs/coordination.md` §2)。
以下是回報,不是修改。同一條已寫進 `docs/coordination.md` §5。

**(一)主題那一側 —— 建議新開 §8.6.6.3 `candidates.syllables`(僅行動端):**

| `placement` | enum `none` \| `above_candidates` \| `keyboard_slot` | `keyboard_slot` | `above_candidates` = iOS;`keyboard_slot` = 三星/語燕 |
| `trigger` | enum `while_composing` \| `on_demand` | `while_composing` | `on_demand` = 要按「选拼音」鍵才出現(iOS) |
| `max_items` | int 0–12 | `0` | `0` = 有多少畫多少 |
| `orientation` | enum `horizontal` \| `vertical` | 由 `placement` 推導 | |
| `height` | length 24–96 | = `bar.height` | 僅 `above_candidates`。⚠ **要寫清楚它與 §8.8.0 高度預算的關係** —— 它是加在鍵盤高度之上,還是吃掉候選列? |
| `background` / `text.*` / `item.*` | 同 §8.6.1–8.6.4 | | |
| `selected.*` | 同上 | | 已經選定的那一段的樣式(語燕會變色) |

**(二)佈局那一側 —— 建議擴充 §9:**

1. **layer 上一個 `syllable_slots: [<key id>, …]`** —— 宣告哪幾格在組字時讓出去。
   ⚠ 這正是 androidkbd 支線 2026-08-09 已經提過的提案(`coordination.md` §5),
   **本文件把它從「一個提案」升級成「規範必須要有的欄位」**,理由是 §5.1:
   位置是風格,而風格必須是宣告出來的。
2. **§9.5 的 action 動詞加一個 `syllables:toggle`**,並照 §9.5.1 加進渲染端的能力宣告
   —— 否則不支援的端會出現一顆「按了沒用」的鍵,那正是 §3.1 的 ⛔ 第一條。

**(三)退化規則(規範性,三條都要寫進去):**

| 情況 | 必須怎麼做 |
|---|---|
| `placement: keyboard_slot`,但當前佈局沒有任何 `syllable_slots` | **退化成 `above_candidates`** + WARNING。⛔ 不得什麼都不畫 |
| 方案給不出音節(沒有 `spelling_hints`) | **整條不出現**,且 `syllables:toggle` 那顆鍵**必須隱藏**(不是變灰、不是按了沒反應) |
| `trigger: on_demand`,但佈局裡沒有任何 `syllables:toggle` 鍵 | **視為 `while_composing`** + WARNING(否則使用者永遠看不到它) |

**(四)還有一個共用層的問題,我沒有解:**
消歧欄的**內容**從哪來。今天 Android 是從候選的 `comment` 反推,而且它**沒有**把選定的音節
送回 librime —— 因為 `t9_pinyin` 的 alphabet 吃不下 `ni`,而 `rs_highlight_candidate`
還沒有 JNI 綁定。**這是共用層 ABI 的問題(協調端的檔案),不是主題格式的問題。**
規範可以先定「擺哪裡」,不必等它。

### 6.4 ⚠⚠ 一條跨端的、`docs/settings-model.md` §4.5 自己寫錯的規則

`docs/settings-model.md` §4.5 寫著:

> **無條件設,不要先判斷方案有沒有這個開關。** 對一個不存在的 switch 呼叫
> `rs_set_option()` 是安全的(librime 只是記下一個沒有人讀的選項)……

**那句話單獨看是對的,但它不足以完成這件事,而規範沒有說第二半。**
**隨附的四個方案沒有一個有 `simplification` 開關** —— 它們用的是互斥選項組
`[zh_hant, zh_hans, zh_hant_hk, zh_hant_tw]`。

| 端 | 做法 | 結果 |
|---|---|---|
| **Android** | 送 `simplification` **+ 整組 radio** | ✅ 對。原始碼註記了模擬器實測:只送 `simplification`,打 `guojia` 仍然得到「國家」 **(測,Android 端做的)** |
| **Windows** | 同上(`common/schema_choice.cc`,明說是「照 Android 驗證過的做法」) | ✅ 對 |
| **macOS** | **只送 `simplification`** (`InputModeBinding.simplificationOption` → `SessionOptions`) | ⛔ **在隨附的四個方案上是一個安靜的空操作** |

**推論(推):** macOS 上把「文字」頁設成「簡體」,或在系統輸入來源選簡體,
**打出來仍然是繁體字**。而四個隨附方案沒有一個是簡體,所以「挑一個字集相符的方案」
那條退路也走不通。⚠ **我沒有在真的 Mac 上跑過** —— 但這正是 macOS 端上一輪宣稱修好的
「選簡體卻打出繁體」,它修的是**挑方案**那一半,**設選項**那一半沒有跟上。

**要動的是規範本身**(`settings-model.md` §4.5 不在本文件的檔案範圍),已寫進 `coordination.md` §5。

**我沒有查的:**

* 第三方(市集)方案的 `speller/alphabet` 分布 —— §2.6 路線 B 的預檢條件
  是照隨附方案推的,34 個市集方案我一個都沒讀。

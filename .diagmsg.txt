## 先更正一件被當成事實的事

交接說法是「翻頁那一關呼叫 rime_console 時不傳方案 id,其餘每一關都傳」。
**不是。** .github/workflows/macos.yml 的 expect_page() 是

    out="$("$C" "$S" "$U" "$1" 1 luna_pinyin_tw 2>&1)"

它有傳。而且四個 commit 一個都沒有動過 macos.yml
(`git log 65bb0af..HEAD -- .github/workflows/macos.yml` 是空的),
本分支的 tree 與 7d49cad **完全相同**(`git diff 7d49cad HEAD` 是空的),
所以紅的那一版跑的就是這一份。

綠的那一關與紅的那一關,真正的差別是**路徑形式**:

    verify_console.sh  ROOT=$(cd .../../.. && pwd)  → 絕對路徑   綠
    翻頁那一關         S=core/data/shared           → 相對路徑   紅

## 為什麼路徑形式可能就是全部

patches/librime-lua@sandbox.patch 第二層(modules.cc 的 kRimeQuadPathSandbox)
第一件事就是:

    local ROOT_USER = normalize(user_dir, nil)
    if not ROOT_USER then error("rimequad: 使用者資料目錄不是絕對路徑: "..) end

而 normalize(p, nil) 只認 "/" 開頭或 "C:/",**對相對路徑回 nil**。
error 之後 C++ 那側走 rimequad_lua_nuke(),把
require / io / os / package / load / debug 全部設成 nil。

而 librime-lua 載 `lua_filter@*luminakey_charset` 的方式是
src/lua_gears.cc:85 的 `lua_getglobal(L, "require")`。require 是 nil
就載不起來 —— 而 librime 對 filter 載入失敗的處置是**整段候選變成空的**。
那正是 core/data/lua/luminakey_charset.lua 檔頭第一個坑寫的東西
(「四個輸入全 0 候選」)。

這也解釋了為什麼在 Android/Linux 重現不出來:emulator 上是用絕對路徑跑的。
若成立,這**不是 macOS 專屬**,是**相對路徑專屬**,而 macOS 只是唯一一條
用相對路徑餵 rime_console 的車道。deploy-only 那一關也用相對路徑卻是綠的,
因為它 return 得比「建立帶 lua filter 的引擎」還早。

以上仍然是假說。這個 commit 的工作是讓 runner 自己回答,不是替它回答。

## 加了什麼

**tools/rime_console.cc**
  · `[diag]` 印 cwd、兩個資料目錄的原字串/是否絕對/realpath。
  · `[diag]` 印六支簡繁開關 + luminakey_charset_off + ascii_*,
    在「session 剛建立」「剛切完方案」「初始」「組字後」四個時點各一次。
  · ⚠ 沒有任何一處新增 rs_snapshot_acquire()。標頭的契約是「每個輸入事件
    只可 acquire 一次」,診斷若自己多 acquire 一次,就會把被診斷的缺陷和
    診斷造成的缺陷混在一起。選項是靠 rs_get_option 讀 context,不碰快照。
    要問「切方案前是哪個方案」得多 acquire 一次,所以那一條關在
    RIME_DIAG_PRESWITCH=1 底下,另外跑一趟。

**core/data/lua/luminakey_charset.lua**
  · 模組本體一跑到就 print 一行 —— **那一行本身就是證據**:
    有它 = require 成功;沒有它 = lua_gears.cc:85 那一步就掛了。
  · 印沙盒標記(stage / io_confined / user_dir / shared_dir)、
    require/io/os/package/utf8 的型別、package.path。
  · M.func 改成 pcall 包住 M.func_impl,把錯誤印出來再**原樣 raise** ——
    librime-lua 預設吞掉 filter 的錯誤,症狀與「這個輸入沒有候選」一模一樣。
    (Lua 5.4 的 pcall 可 yield,所以包得住會 yield 的東西;5.1 不行。)
  · 印 M.pick 挑了哪一個字集、字集載入成功/失敗、進幾個候選出幾個、
    退回機制有沒有觸發。全部印到 **stdout**(GitHub 收得到),不是 glog。
  · 上限 24 行,免得單音節上千候選灌爆 log。

**.github/workflows/macos.yml** 兩個新關卡,**兩個都永遠綠**(是問問題的,
不是把關的;把關的仍然是原本那一關,維持硬失敗):
  · `[diag] verify_console.sh:傳方案 id 與不傳,各一次`

    librime 對 lua 載入失敗的抱怨正是走那條路),最後一張彙整表:
        A 絕對＋方案id   B 相對＋方案id      ← 綠/紅那兩條路
        C 絕對＋不傳     D 相對＋不傳

        G 守門關掉＋絕對  H 守門關掉＋相對    ← **刀口**
        I RIME_DIAG_PRESWITCH   J zh_hans=1
    G/H 變成 5 → 兇手是守門的判斷邏輯;
    G/H 還是 0 而 A=5 B=0 → 兇手是相對路徑那條鏈(關不關守門都一樣,

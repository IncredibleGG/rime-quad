# 介面設計規範（四端共用）

> 「UI 也不對。我給了你一個對照的 UI，大概像他那樣。但是要比他好看。」
>
> 「比他好看」沒辦法驗收，所以這份文件把它翻譯成 **§2 的一張檢核表**。
> 檢核表上的每一條都能被 CI 或 code review 對照，而不是靠品味。
>
> **我不是專業美工。** 所以這裡不會出現「更現代」「更精緻」這種句子。
> 每一個決定都寫成**規則 + 數值 + 理由**，讓你看得懂、也讓你能指著說「這裡不對」。
> 你要反駁的話，反駁的對象是理由，不是我的品味。

| | |
|---|---|
| 維護者 | 誰先實作誰補，**只加不刪別人的段落** |
| 管的範圍 | **App 這一側的畫面**：引導、設定、方案市集、換鍵、備份、診斷 |
| **不管**的範圍 | 軟鍵盤本身、候選窗、狀態列 —— 那些由 `docs/theme-format.md` 的 YAML 驅動 |
| 目前實作 | Android（資訊架構符合；**設計語彙差距很大** —— 現在用 26 種間距值、17 種字級，見 §3.1）、macOS（資訊架構符合，版面待對齊） |
| 未實作 | Windows、iOS |

## 0. 這份文件與其他規範的關係

三份文件管三件不同的事，**不要互相覆蓋**：

| 文件 | 管什麼 | 誰能改 |
|---|---|---|
| `docs/theme-format.md` | 鍵盤與候選窗長什麼樣（一份 YAML 的規範） | **只有 macOS 端** |
| `docs/settings-model.md` | **有哪些**設定項、叫什麼 id、存在哪一層 | 誰先實作誰補 |
| **本檔** | 那些設定項**畫成什麼樣子**、用哪個元件、寫什麼字 | 誰先實作誰補 |

**邊界很明確**：軟鍵盤一個顏色都不吃本檔的色票（Android 端 `ui/Theme.kt` 的檔頭已經寫死這一條），
本檔也不定義候選窗的任何一個數值。**兩邊撞到的時候，鍵盤那一側以 `theme-format.md` 為準。**

還有一條紀律先講在前面，因為它比任何視覺決定都重要：

> ⚠ **做不到的功能不要畫出來。**
> 不留一頁空的、不留一排灰掉的控制項、不留一顆按了什麼都不會發生的按鈕。
> 這個專案抓到過五個「畫面完全正常、自動化全過、使用者按了沒反應」的東西
> （重輸鍵、中英鍵、按下後顏色回不來、工具列 emoji 鍵、退格），
> 而 macOS 端已經因此把整頁「我的詞庫」下架。
> **一頁看起來正常但其實沒用的畫面，比沒有這一頁更糟**，因為使用者只會覺得是自己做錯了。

## 1. 對照研究

### 1.1 對照品：中州韻助手 rimetool

**這一節的資料怎麼來的（先講可信度，因為後面每一條結論都靠它）**

| 來源 | 我看到什麼 | 可信度 |
|---|---|---|
| `gitee.com/wubi98/rimetool`（使用者給的那個） | 是**配置與碼表的倉庫**，不是程式本體。裡面是 weasel / fcitx5 / ibus / squirrel 的設定檔、`.dict` 碼表、`*.custom.yaml` | 直接讀到 |
| `github.com/yanhuacuo/rimetool`（程式本體） | 功能自述：線上加詞、可視化詞庫管理、詞條調序、開關控制、一鍵換版式、註解符號、自訂 YAML 解析核心 | 專案自述 |
| Release 1.3.2 說明 | 逐字：「添加【配置管理】，一键下载配置包」「修正对雾凇、薄荷的功能控制参数」「修正【薄荷模式】下，在线加词的逻辑问题」「优化补丁读写机制」。並註明配置包放在 Gitee，**是加密壓縮檔，解壓密碼 `rimetool`**，原因是 Chrome 擋含批次腳本的壓縮包 | 直接讀到 |
| 小眾軟體論壇（appinn）討論串 | 版面是**分頁式**，看得到的分頁／面板：**上屏行为、主题参数、候选框排版、词库管理、导表**。使用者回報的問題：初學者缺乏安裝指引與方案適配說明、點「自動上屏配置」會崩潰、UI 偏移、只支援薄荷與雾凇兩套方案 | 二手，但具體到可用 |
| 舊版（C++ 重構版）的作者部落格 | 面板：快捷路徑（使用者目錄／程式目錄／日誌目錄）、資料備份（一鍵到桌面／文件並以時間戳建資料夾）、進程守護、開機啟動、資料同步、算法服務更新（內建 rime.dll）、擴充詞庫管理 | 二手 |
| 技術棧 | 自述為 **QML + C++，使用 FluentUI**，支援 Windows / Linux / macOS | 二手 |

⚠ **我沒有安裝它、沒有截圖、沒有量過任何一個數字。**
`docs/competitive-review.md` 那份報告的每一個數字都是實測的；**這一節不是**。
所以下面的比較只敢比**資訊架構與用字**這種從文字就看得出來的東西，
不比間距、不比配色、不比動效 —— 那些我沒有證據。

**看得出來的三件事**

1. **它的分頁名全部是 RIME 的內部概念。** 「上屏行为」「候选框排版」「导表」「码表」——
   這幾個詞對 RIME 老手是精準的，對其他人是零。
   使用者對我們的原話是「你這個第一屏 99% 的人看不懂」，而 rimetool 的第一屏
   是**同一個病**的加強版：它把 YAML 的每一個欄位都做成一個控制項。
2. **它的核心賣點是「參數全面可視化」。** 也就是把 YAML 換成滑桿與勾選框，
   但**要調哪一格仍然要你自己知道**。這是一個給 RIME 老手省時間的工具，
   不是一個讓新手能開始打字的產品。**我們的使用者是麻瓜，所以這條路我們不能走。**
3. **它把「拿到能用的配置」外包給一包壓縮檔。** 1.3.2 的頭條功能是「一鍵下載配置包」，
   而那包東西是**放在 Gitee 的加密壓縮檔，密碼是 `rimetool`**。
   加密不是為了安全（密碼公開），是為了繞過瀏覽器的下載攔截。
   對一個「無審查、經得起審計」的產品來說，這正是**反面教材**。

### 1.2 對照品：Gboard / 微軟拼音 / 搜狗

| | 分頁／群組 | 看得出來的問題 |
|---|---|---|
| **Gboard**（Android） | Languages / Preferences / Theme / Text correction / Glide typing / Voice typing / Dictionary / Search / Advanced | 九個平行分頁，**沒有層級**。「Preferences」「Advanced」兩個名字等於沒說。使用者要找「鍵盤高度」得先猜它在 Preferences 還是 Advanced |
| **微軟拼音**（Windows 11） | 常规 / 按键 / 外观 / 词库和自学习 / 高级 | 五頁，最乾淨的一個對照。但「词库和自学习」是兩件事綁在一起，而且入口深到要走 設定 → 時間和語言 → 語言和區域 → 三點 → 語言選項 → 三點 → 鍵盤選項 |
| **搜狗**（Windows／Android） | 外观 / 词库 / 按键 / 高级（高級底下還有 AI 助手、輸入助手、常規候選、候選擴展、升級設定、桌面寵物、推薦設定） | 「高级」是垃圾桶：把 AI、桌寵、推薦全部倒進去。這是分類失敗的典型症狀 —— 分不進去的東西越來越多 |

**三家共同做對的一件事**：分頁名稱用**使用者的詞**（外觀、按鍵、詞庫），不用引擎的詞。
**三家共同做錯的一件事**：都有一個叫「高級 / Advanced」的無底洞。

> 我們的 §5.1 因此有一條硬規則：**「進階」頁只放四類東西**（修復、匯入匯出、語言、診斷），
> 想往裡面塞第五類的時候，那代表分類本身要重做，不是進階要變大。

### 1.3 我們要比它們好在哪（每一條都附驗法）

不是「更現代」。是這八條，每一條都指得出對照對象，也都有辦法檢查。

| # | 我們要贏的地方 | 對照 | 怎麼驗 |
|---|---|---|---|
| 1 | **不需要先懂 RIME 才會用。** 畫面上不出現任何引擎內部的詞 | rimetool 的「上屏行为／候选框排版／导表」；微軟的「词库和自学习」 | 禁用字掃描（§6.7），加上「每一項都必須有一句白話」的型別強制 —— macOS 端已成立，另兩端照抄 |
| 2 | **不必先下載一包東西才能打字。** 四個方案在安裝包裡，首次部署後直接可打 | rimetool 的頭條功能是「一鍵下載配置包」，而那包是 Gitee 上密碼 `rimetool` 的加密壓縮檔 | 全新安裝 → **不開連網** → 打得出字。Android 的 `verify_rime_compose.sh` 已經是這一關 |
| 3 | **離線可以被證明，不是被宣稱。** 有一整頁列出「連過哪些地方」，而且開關沒開過時它必須是空的 | 三家對照品都沒有這樣一頁 | `audit_offline.sh` 的單一出口 grep + 連網紀錄的反向測試（被擋下來的嘗試**不記**） |
| 4 | **下載回來的東西看得懂也擋得住。** 索引有簽章、安裝前檢查內容、第三方 lua 走沙盒 patch | rimetool 是共用密碼的加密 zip | `ArchiveGuard` 測試 + `patches/librime-lua@sandbox.patch` 的稽核 |
| 5 | **同一份設定在四台裝置上是同一件事。** 四端共用 `settings-model.md` 的 id 與分頁 | rimetool 只有桌面三端、只支援兩套配置；Gboard 沒有桌面端；微軟拼音只有 Windows | 三端的設定目錄測試比對同一份 id 清單（§9 的落地對照表） |
| 6 | **危險的東西看起來就危險。** 破壞性動作一律外框＋危險色＋頁面最底＋二次確認寫出後果 | 三家都把「重置」和一般設定混在同一張清單裡 | 檢核表 C1／C2：實心按鈕不得帶危險色；帶危險色的控制項必須在該頁最後一個區塊 |
| 7 | **裝好之後知道下一步。** 第一屏最上面固定回答「現在能不能打字」，而且**由系統狀態推導，不靠自己記的旗標** | appinn 對 rimetool 的第一條抱怨是「初學者缺乏安裝指引」；語燕的精靈用自己的旗標判定完成，使用者從系統設定先設好反而被困住；Trime 按 SKIP 之後直接崩潰迴圈 | 反向測試：從系統設定把 IME 關掉，第一屏必須**立刻**變回「還不能打字」 |
| 8 | **看得到的每一顆都摸得到。** 不留灰控制項、不留死按鈕、做不到的整頁拿掉 | —（這條是我們自己付過學費的：五顆死鍵、一頁下架的詞庫） | 無障礙動作測試（自動）+ 逐項點過（**只有人做得到**） |

### 1.4 明確**不**抄的

- **rimetool 的「主題參數所見即所得」**（陰影、外擴、間距、圓角逐項可調）。
  那是把 YAML 換成滑桿，使用者仍然要知道「外擴」是什麼。
  我們給的是**幾套做好的配色 + 一個字級 + 一個深淺**，三個選擇解決同一件事。
- **rimetool 的「导表」與碼表逐格編輯。** 我們的使用者詞庫是三欄 TSV，
  而且那一頁在 macOS 端已經因為 librime 讀不到而下架（`settings-model.md` §5）。
  在它變綠之前，四端都不要畫這一頁。
- **搜狗的 AI 助手 / 桌面寵物 / 推薦設定。** 與離線定位直接衝突。
- **Gboard 的雲候選。** 同上。
- **語燕的「花漾字」。** 與「正確排版」的定位相反（`competitive-review.md` §7 已記）。
- **任何一家的「高級」無底洞。** 見 §5.1。

## 2. 檢核表：「比它好看」的可驗收版本

這是本文件最重要的一節。**每一端的 CI 或 code review 對照這張表。**

`機器` = 寫得出自動檢查；`人` = 只有人做得到，請列進該端的真機驗證清單。

### A. 一眼看得到該做什麼

| # | 條目 | 檢查 |
|---|---|---|
| A1 | **每一屏最多一顆實心按鈕。** 其餘一律外框或純文字 | 機器：掃 UI 樹，`filled` 樣式的按鈕每屏 ≤ 1 |
| A2 | **每一頁的主要操作在不捲動的情況下看得到。** 「主要操作」= 使用者來這一頁的理由 | 人：每頁在最小支援尺寸下截一張圖，主要操作必須在第一屏內 |
| A3 | **第一屏最上面回答「現在能不能打字」。** 不能打字時，同一張卡片裡有直達的按鈕 | 機器：第一屏的第一個非標題元素是狀態卡或連網卡；狀態由系統查詢推導。反向測試：關掉 IME 之後狀態必須翻轉 |
| A4 | **每一個第二層都有看得見的返回。** 系統返回鍵是第二條路，不是唯一那條 | 機器：每個非首頁的頁面都有 `PageHeader` 或等價物 |

### B. 沒有裸露的技術名詞

| # | 條目 | 檢查 |
|---|---|---|
| B1 | **禁用字表（§6.7）一個都不准出現在使用者看得到的字串裡** | 機器：字串資源掃描 + 允許清單 |
| B2 | **每一個設定項都有一句白話說明它會改變什麼**，而且「白話」不是 Optional | 機器：型別強制（macOS 已成立）+ 目錄測試 |
| B3 | **畫面上不出現百分比、毫秒、倍數、像素。** 使用者要的是「再大一點」，不是 `1.15` | 機器：掃使用者可見字串裡的 `%`、`ms`、`px`、`×`、`倍`。例外只有「下載進度」與「診斷區塊」，且必須列進允許清單 |
| B4 | **不出現任何 id。** schema id、layout id、layer id、bundle id、套件名 | 機器：同 B1。診斷區塊例外 |
| B5 | **診斷區塊永遠是英文、等寬字、而且旁邊有一句當地語言說「這些數字是給我們看的，你不用懂」** | 機器：診斷字串不進在地化資源；該句提示必須存在 |

### C. 危險操作有明確的視覺區隔

| # | 條目 | 檢查 |
|---|---|---|
| C1 | **破壞性動作一律：外框按鈕 + 危險色文字 + 透明底。** 不得用危險色實心底 | 機器：不存在同時具備 `filled` 與 `error` 的控制項 |
| C2 | **破壞性動作在該頁最後一個區塊**，與上面隔一條 hairline + 一個 s7 空白 | 機器：帶危險色的控制項的順序索引 = 該頁最後 |
| C3 | **二次確認的確認鍵寫出它會做什麼**（「刪掉這 42 個詞」），不是「確定」 | 機器：確認對話框的主鍵文字不得屬於 {確定, 好, OK, 是, Yes} |
| C4 | **二次確認的預設焦點在「取消」** | 機器：對話框宣告的預設按鈕 = 取消 |
| C5 | **不可逆的動作要同時點名「會消失的是什麼」與「不會消失的是什麼」**，兩句都要 | 人：讀那段文案 |

### D. 誠實

| # | 條目 | 檢查 |
|---|---|---|
| D1 | **沒有灰掉的控制項用來代表「這個平台做不到」。** 做不到就整頁／整項拿掉 | 機器：`disabled` 的控制項必須同時提供「為什麼」的文字；否則不准 disabled |
| D2 | **每一顆按鈕都真的做了它宣稱的事** | 人：逐項點過（本專案抓到過五個反例，全部畫面正常、自動化全過） |
| D3 | **超過 300ms 的動作要有進度；無法預估的動作顯示經過秒數，不假裝有百分比** | 機器：非同步動作必須綁定進度狀態。人：實際按一次「重新整理字詞」 |
| D4 | **成功 → 短暫提示自動消失；失敗 → 停在對話框上不自動關** | 機器：成功路徑不得產生 modal |
| D5 | **錯誤訊息叫使用者去看的東西，在那條失敗路徑上必須真的存在** | 人：對每一條錯誤訊息走一次它的失敗路徑（`coordination.md` §3 的 `logcat.txt` 事故） |

### E. 空狀態與載入

| # | 條目 | 檢查 |
|---|---|---|
| E1 | **每一個可能為空的清單都有空狀態**，而且空狀態說三件事：為什麼是空的、這是不是正常、下一步按哪裡 | 機器：清單元件必須提供 `empty` 分支。人：讀那三句話 |
| E2 | **不得只畫一個插圖配「沒有資料」** | 人 |

### F. 一致與可讀

| # | 條目 | 檢查 |
|---|---|---|
| F1 | **所有間距都落在 §3.1 的階梯上** | 機器：掃 `dp`／`pt` 字面值。⚠ **先讀 §3.1 的「F1 的範圍」** —— 間距、圓角、元件尺寸是三個不同的集合，混在一起掃會把 1dp 的分隔線判成違規，而**一條永遠紅的檢查會被關掉** |
| F2 | **所有字級都落在 §3.2 的六階上** | 機器：掃 `sp`／`pt`。現況 17 種（§3.2） |
| F3 | **文字對比度符合 §3.4 的門檻**（小字 ≥ 4.5:1、大字與非文字 ≥ 3:1、分隔線 ≥ 1.4:1） | 機器：色票表算得出來，寫成單元測試 |
| F4 | **深色模式只換色票，不動版面、間距、字級、層級** | 機器：深淺兩份色票的**鍵名集合完全相同**；版面程式碼裡不得出現 `isDark` 分支 |
| F5 | **觸控目標 ≥ 48dp（行動）／點擊目標 ≥ 28pt（桌面）** | 機器：掃元件的最小高度宣告 |
| F6 | **每一個控制項都有無障礙名，狀態型控制項還要有狀態描述** | 機器：`KeyA11yTest` 的形狀。人：TalkBack／VoiceOver 逐項摸過 |

### ⚠ G. 這張檢核表自己會不會失效

| # | 對每一條機器檢查的要求 |

## 3. 設計語彙

### 3.1 間距階梯

**八階，沒有第九階。行動端一律是 4 的倍數，唯一的例外是 `s1`。**
需要一個不在階梯上的數值時，改階梯（並通知四端），不要在單一畫面上例外。

| token | 行動 dp | 桌面 pt | 用在哪 |
|---|---|---|---|
| `s1` | **2** | 2 | 標題與它正下方的副標之間。**這是唯一不是 4 的倍數的一階** —— 4 會讓那兩行看起來不像同一組 |
| `s2` | 4 | 4 | 圖示與它的文字之間 |
| `s3` | 8 | 6 | 同一組控制項彼此之間；小標題與它管的控制項之間 |
| `s4` | 12 | 10 | 卡片內一列的上下 padding |
| `s5` | 16 | 12 | 卡片內的左右 padding；卡片與卡片之間 |
| `s6` | 20 | 16 | 畫面左右邊距（行動端） |
| `s7` | 24 | 20 | 區塊與區塊之間（有小標題的那種） |
| `s8` | 40 | 32 | 頁面頂端與底端的留白 |

**桌面欄怎麼來的**：行動值 × 0.8，四捨五入到最接近的偶數。
所以桌面欄**不是** 4 的倍數（6、10），這是刻意的 —— 桌面的密度本來就比行動端高。

**兩條用法規則：**

1. **同一組東西之間的距離，必須小於它們與外面的距離。** 這是「分組」唯一可靠的手段
   —— 比框線、比顏色、比分隔線都可靠。分隔線只是輔助。
2. **不要用兩個相鄰的階數表達不同的意思**（例如 s3 與 s4 混用在同一種關係上）。
   看不出差別的差別等於沒有差別，只會讓四端各自漂移。

⚠ **F1 檢查的是「有沒有落在這八個值裡」，不是「能不能被 4 整除」。**
允許集合寫死成上面兩欄的值，多一個少一個都要改這張表。

#### F1 的範圍（不寫清楚的話這條檢查會誤傷）

`.dp` 字面值不是全部都是間距。**三個集合各管各的，不要混在一起掃**：

| 集合 | 允許值（行動 dp） | 出現在哪 |
|---|---|---|
| **間距** | 2, 4, 8, 12, 16, 20, 24, 40 | `padding`、`spacedBy`、`Spacer` 的高度 |
| **圓角**（§3.3） | 8, 9, 11, 16 | `RoundedCornerShape` |
| **元件尺寸**（§3.6） | 1（hairline）, 48, 58 | `height`、`heightIn(min=)`、線寬 |

`0.dp`（陰影高度）不受管，因為它表達的是「不要陰影」，不是一個間距。

#### 現況與這份階梯的距離（實測，2026-08-09）

我在 `home/`、`prefs/`、`net/`、`store/` 四個套件的 App 側程式碼上數過：

| | 現在用了幾種值 | 本規範允許幾種 |
|---|---|---|
| `.dp` 字面值 | **26 種**（含 1.5、3、6、9、11、14、18、22、26、28、30、34、52…） | 間距 8 + 圓角 4 + 尺寸 3 |
| `.sp` 字面值 | **17 種**（含 11.5、14.5、15.5、19、23、34…） | 6（§3.2） |

⚠ **這是一個大幅收斂，不是一個微調。**
`s7 = 24` 與現況的 `26.dp` 只差 2dp（沒有人看得出來），但 26 種 → 15 種是真的要動很多行。

⚠ **而且我沒有把那 26 種逐一分類成間距／圓角／尺寸。**
所以「現在有幾條違規」這個數字**我沒有**，只有「現在有幾種值」。
接這條檢查的人第一件事是分類，不是直接掃 —— 直接掃會把 `1.dp` 的分隔線也判成違規，
而**一條永遠紅的檢查會被關掉**，那比沒有這條檢查更糟。

### 3.2 字級階梯

**六階，沒有第七階。**（Android 端現在用 **17 種** `sp` 值 —— 見 §3.1 的實測表。
這一階梯同樣是收斂，不是微調。）

| token | 行動 | 桌面 | 字重 | 用在哪 | 不要用在 |
|---|---|---|---|---|---|
| `t1` 頁標題 | 27sp | 22pt | SemiBold | 每頁最上面那一行，**一頁只有一個** | 第二層（第二層用 t2） |
| `t2` 區段標題 | 17sp | 15pt | SemiBold | 第二層的頁首、對話框標題 | 一般小標題 |
| `t3` 列標題 | 16sp | 13pt | Medium | 設定項的名字、卡片內的主要文字 | 說明文字 |
| `t4` 現值 | 13.5sp | 12pt | Regular | 列右側的現值、按鈕文字 | 標題 |
| `t5` 說明 | 12.5sp | 11pt | Regular | 白話說明、小標題、輔助文字 | 主要內容 |
| `t6` 診斷 | 12sp 等寬 | 11pt 等寬 | Regular | **只有**診斷區塊 | 其他任何地方 |

**三條用法規則：**

1. **字級只表示層級，不表示重要性。** 「這個很重要」用位置（放上面）與顏色（重點色）表示，
   不要放大字級 —— 放大之後下一個重要的東西就沒有階可以用了。
2. **一行中文超過 40 個字就要限寬。** 超過的時候眼睛回不到行首。桌面端的內容欄因此有上限（§5.1）。
3. **列標題永遠一行，長了就截尾。** 這一條是實測撞出來的：在地化成英文之後，
   右邊的現值把整列吃光，左邊的「Text」被擠成兩行的「Te / xt」—— 一個標題從中間斷開，
   看起來像畫面壞了。**現值可以折兩行，但寬度不得超過該列的一半。**

### 3.3 圓角

**四個值（`16 / 11 / 9 / 8`），巢狀時內層 = 外層 − 2~5。**

| 用途 | 行動 dp | 桌面 pt |
|---|---|---|
| 大：卡片、對話框、面板 | 16 | 10 |
| 中：分段控制外框、晶片、輸入框 | 11 | 7 |
| 中的內層：分段控制被選中的那一格 | 9 | 6 |
| 小：圖示容器、縮圖、進度條 | 8 | 5 |
| 按鈕 | 依平台原生 | 依平台原生 |

（`14dp` 的輸入框是現況，本表把它併進「中」的 11 —— 這是本節唯一一處
與 Android 現況不同的值，改動 1 行。）

**規則：按鈕的圓角跟平台走，不跟我們走。** 一顆長得不像該平台按鈕的按鈕，
使用者不會確定它按不按得下去 —— 這比「風格統一」重要。

### 3.4 顏色語意

**先講規則，再給色票。** 因為問題從來不是「哪個綠色比較好看」，是「什麼時候可以用彩色」。

**三條硬規則：**

1. **一頁最多一個彩色重點。** 彩色只回答兩個問題：**該點哪裡**、**哪裡出事了**。
   不用來表示分類、不用來裝飾、不用來給圖示上色。
2. **不得只用顏色傳達資訊。** 每一個用顏色表示的狀態，都要另外有文字或形狀。
   （色覺障礙、深色模式、低亮度螢幕、截圖轉灰階 —— 四種情況都會讓顏色失效。）
3. **深色不是另一份設計。** 版面、間距、字級、層級完全不動，只換色票。

**色票與語意**（值取自 Android 端 `ui/Theme.kt` 的現況，它是目前唯一在真裝置上被使用過的一份）：

| 角色 | 淺色 | 深色 | 什麼時候用 | 什麼時候**不要**用 |
|---|---|---|---|---|
| `background` 底 | `#F4F6F5` | `#0D1012` | 視窗／畫面的底 | 卡片內部 |
| `surface` 卡片 | `#FFFFFF` | `#171B1D` | 卡片、對話框、分段控制**被選中**的那一格 | 大面積的底 |
| `surfaceVariant` 凹槽 | `#F2F5F4` | `#121618` | 分段控制的軌道、**未**選中的晶片、輸入框內 | 需要浮起感的東西 |
| `onSurface` 主要文字 | `#14181A` | `#ECEFEE` | 頁標題、列標題 | 說明文字（會讓一屏全是黑字，沒有主次） |
| `onSurfaceVariant` 次要文字 | `#454F51` | `#B9C3C2` | 白話說明、現值、小標題、非互動圖示 | 列標題 |
| `primary` 重點 | `#1F6F63` | `#63C3AC` | 該頁**唯一**的實心按鈕；被選中的狀態 | 標題、圖示著色、任何裝飾 |
| `onPrimary` | `#FFFFFF` | `#08110F` | 實心按鈕上的字 | — |
| `primaryContainer` 選中底 | `#D7EDE7` | `#17322D` | 被選中的晶片的底 | 一般卡片 |
| `error` 危險 | `#B3261E` | `#FF8A80` | 破壞性動作的文字與外框；錯誤訊息 | 一般提醒、「注意」、必填標記 |
| `errorContainer` 錯誤底 | `#F9DEDC` | `#3A1512` | 錯誤橫幅的底 | 破壞性**按鈕**的底（見 §4.9） |
| `outline` 分隔 | **`#C4CDCC`** ⚠ | **`#363E40`** ⚠ | 卡片內列與列之間的 1px 線；區塊之間的 hairline | 卡片外框（卡片靠底色差異區隔，不靠框） |

**為什麼只有一個重點色**：青瓷綠 `#1F6F63` 刻意避開所有競品的識別色
（語燕橘紫、三星藍、Gboard 藍、微軟藍）。**而且刻意只有一個** ——
畫面上「該點哪裡」必須不必讀字就看得出來，多一個彩色就少一分這個能力。

### 3.5 深淺色規則

1. **`followSystem` 是預設，而且是三態的第一態。** 只有兩態的話，使用者按過一次之後
   就回不到「讓系統決定」了。這一條對每一個「跟著○○」的設定都成立。
2. **深色時重點色提亮、降飽和**（`#1F6F63` → `#63C3AC`），實心按鈕上的字改成近黑
   —— 亮青底配白字**實測只有 2.11:1**，換成 `#08110F` 之後是 9.05:1。
3. **卡片與底只差一階**（`#171B1D` vs `#0D1012`），靠 1px 分隔線切開，**不靠陰影**。
   深色下用陰影的結果是「一坨黑」。
4. **深色不用純黑 `#000000` 當底，不用純白 `#FFFFFF` 當文字。** 純黑在 OLED 上會讓
   捲動時出現拖影，純白在深底上會有光暈。
5. **版面程式碼裡不得出現 `isDark` 分支**（F4）。深淺的差別必須全部收在色票表裡，
   否則兩個模式會慢慢長成兩份設計，而且只有一份會被測到。

### 3.6 動效、焦點、觸控目標

| 項目 | 值 | 理由 |
|---|---|---|
| 一般狀態轉換 | 150ms，ease-out | 短到不會擋路，長到看得出發生了變化 |
| 頁面進出 | 220ms | |
| 對話框出現 | 180ms；消失 120ms | 消失要比出現快，否則像卡住 |
| 系統關閉動畫時 | **全部 0ms，但狀態照樣改變** | 不是「不動」，是「瞬間到位」。做成不改變狀態是常見的 bug |
| 觸控目標最小 | 48 × 48 dp | |
| 設定列的最小高度 | 58 dp | 兩行文字（t3 + t5）加上下 padding |
| 桌面點擊目標最小 | 28 × 28 pt | |
| 鍵盤焦點環 | 2pt 重點色，圓角比元件大 2 | 桌面端必須全鍵盤可操作 |

**動效規則：動效只用來說明「東西從哪來、往哪去」。** 不用來吸引注意、不用來表示品質。
任何一個動畫如果拿掉之後畫面仍然說得通，就拿掉。

## 4. 元件清單

每一項都寫：**什麼時候用 / 什麼時候不要用 / 硬性規則**。
四端的原生對應見 §9。

### 4.1 開關（Switch）

- **用**：真正的二選一，而且**兩個狀態都有明確的名字**（開／關、允許／不允許），
  改了立刻生效，沒有第三態。
- **不要用**：有「跟著系統／跟著方案／跟著主題」這種第三態的設定 —— 那是分段控制。
  也不要用在「需要按下確認才生效」的東西上（開關的心智模型是立即）。
- **規則**：
  - 開關的標題必須是**肯定句**，不得是否定句。「不要顯示號碼」打開＝不顯示，
    使用者要在腦裡做兩次否定。
  - 開關右邊，標題與說明在左邊，整列可點（點列＝切換）。
  - **切換之後如果需要重新部署才生效，必須當場說**（一行小字），不要等使用者發現。

### 4.2 分段控制（Segmented）

- **用**：**2–4 個**互斥選項，而且**全部看得到**比「點開再選」重要。
  這是本產品第二層的預設控制項。
- **不要用**：選項 ≥ 5 個（會擠成一團，中文會被截斷）；選項的文字長度差很多；
  選項會隨資料變多（配色、方案清單）。
- **規則**：
  - 「跟著○○」永遠是**第一格**，而且是預設。
  - 每一格的文字**一行、不截斷**。做不到就代表選項太多或文字太長，改用 §4.4。
  - **選項本身可以是範例**：標點那一題直接寫「，。中文」與「, . 英文」，
    比任何說明文字都清楚。

### 4.3 單選晶片（Chip）

- **用**：選項數量**不固定**、會隨資料變多（配色目前 6 個、日後更多）。
- **不要用**：選項固定且 ≤ 4（用分段控制，位置固定比較好記）。
- **規則**：選中用 `primaryContainer` 底 + 字重加粗（**兩個訊號**，不能只有顏色）。

### 4.4 下拉／彈出選單

- **用**：≥ 7 個互斥選項、有天然順序、而且使用者**知道自己要找什麼**。
- **不要用**：
  - 選項 ≤ 5 → 分段控制或晶片；
  - 選項需要預覽（配色）→ 縮圖卡片；
  - 行動端上**不要用系統 Spinner** —— 選中態在小螢幕上看不見，改用「點進去的第二層清單」。
- **規則**：收合時必須顯示**現在選的是什麼**，不得只顯示標題。

### 4.5 清單項（列）

第一層與第二層的列長得不一樣，這是刻意的。

| | 第一層（首頁的列） | 第二層（設定頁的列） |
|---|---|---|
| 內容 | **只有名字 + 現在的值 + `›`** | 名字 + 一句白話 + 控制項 |
| 為什麼 | 大多數人來設定只是想確認一件事，看一眼就走 —— 「注音 · 大千排列」這行灰字本身就是最好的說明 | 到了第二層就是要改東西，這時才需要白話 |
| 最小高度 | 58dp | 58dp |
| `›` | 有 | **沒有**（第二層是終點） |

**規則：深度上限是兩層，第二層一定是終點。**
唯一的例外是「下載更多打字方式」（市集本質上是另一個世界的入口）與「換鍵」
（它有自己的一整套互動）。**新增第三層之前先寫進 `coordination.md` §5。**

### 4.6 可排序清單

- **用**：順序本身有意義（方案清單 —— 第一個是預設，順序即切換順序）。
- **不要用**：只是想讓使用者「整理」。排序是成本，沒有回報就不要收。
- **規則**（三條，缺一不可）：
  1. **拖曳把手必須看得見**（`⠿`），不能只靠長按。長按是隱藏功能。
  2. **必須同時提供「上移／下移」的無障礙動作** —— TalkBack 與 VoiceOver 拖不動東西。
     這一條和 `docs/accessibility.md` 抓到的「念得出名字但輕點兩下什麼都不會發生」是同一類缺陷。
  3. **順序改變之後要立刻可見地說出結果**：「現在預設是注音 · 臺灣正體」。
     使用者拖完不該還要自己推導發生了什麼。

### 4.7 空狀態

**三件事，缺一不可**：

1. **為什麼是空的**（「你還沒有加過任何詞」）
2. **這是不是正常**（「這是正常的，大部分人不需要加」）
3. **下一步按哪裡**（一顆按鈕，或明確說「不用做什麼」）

**不得**只畫一個插圖配「沒有資料」。
**連網紀錄那一頁的空狀態最重要**：它的空必須被解釋成「證據」，不是「壞掉」——
「還沒有連過任何地方。你沒有打開過連網開關，所以這裡是空的 —— 這正是你可以自己確認的方式。」

### 4.8 載入中

| 時間 | 做什麼 |
|---|---|
| < 300ms | **什麼都不顯示。** 閃一下比等一下更糟 |
| 300ms – 2s | 原地的細進度條或骨架，**不遮蓋**畫面 |
| > 2s | 明確的進度區塊 + **經過的秒數** + 一顆「在背景跑」 |
| 無法預估 | 不定式進度條 + 經過秒數 + 一句「第一次通常要 10–20 秒」 |

⚠ **`rs_deploy()` 不提供百分比，唯一誠實的進度是經過的秒數。**
（實測：模擬器 7.2 秒、S24U 首次 12.5 秒。真機回報過這個 bug，原話是「按了沒反應」。）
**不要畫一條會自己跑到 90% 然後停住的假進度條。**

### 4.9 危險操作

- **樣式**：外框按鈕 + `error` 文字色 + **透明底**。
- **不得**用 `error` 實心底 —— 實心底是「主要動作」的視覺，會讓最危險的東西看起來最該按。
- **位置**：該頁最後一個區塊，上面隔一條 hairline + 一個 s7 空白。
- **二次確認**：
  - 確認鍵寫出它會做什麼（「刪掉這 42 個詞」），不是「確定」。
  - 預設焦點在「取消」。
  - 內文同時點名**會消失的是什麼**與**不會消失的是什麼**。
- ⚠ **「全部回復預設」不歸零「已經發生過的事實」**（看過首次說明、走完引導）。
  那些不是設定；清掉的話使用者按一次就會被丟回引導頁。

### 4.10 錯誤

**公式（三段，缺一不可）**：

```
[發生了什麼]。[為什麼]。[你現在可以做什麼]。
```

- 第三段必須是**使用者做得到的動作**，不是「請聯絡開發者」。
- **不得**把內部錯誤字串直接倒出來。技術細節放在「顯示詳細資訊」底下，預設收起。
- ⚠ **訊息叫使用者去看的東西，在那條失敗路徑上必須真的存在。**
  本專案有過一次：「鍵盤在 120s 內沒有出現」叫人去看 `logcat.txt`，
  而那個檔案只在**成功路徑**的尾端才寫 —— 唯一需要它的時候它不存在。
- **失敗停在畫面上不自動關；成功用短暫提示自動消失。**
  成功之後彈一個要按「知道了」的對話框，等於在他已經達成目的之後多收一次過路費。

### 4.11 唯讀資訊（診斷）

- **永遠英文、等寬字、可整段複製、旁邊一句當地語言的「這些數字是給我們看的，你不用懂」。**
- 理由：它不是介面文字，是一份要被貼進 issue 的回報載荷。翻譯它會讓收到的 issue
  有三種語言的欄位名，grep 不到也對不起來。
- **所有 id（schema id、bundle id、套件名）只能出現在這裡。**

### 4.12 兩種不要做的東西

- ⚠ **不要做「編輯 YAML 的文字框」然後叫它視覺化編輯。** 那是把問題丟回給使用者。
- ⚠ **不要做滑桿。** 使用者要的是「再大一點」，不是 `1.15`。
  唯一的例外是**鍵盤高度**，而它不是滑桿 —— 是**在鍵盤上原地拖曳上緣**
  （`competitive-review.md` §4.2 把這個互動評為對照品裡最好的一個）。

## 5. 版面

### 5.1 桌面：側欄還是分頁？

**判準（規範性，不憑感覺）：**

設 `N` = 頁數，`M` = 最長那一頁的設定項數。

```
N ≤ 4  且  M ≤ 6   →  分頁（tabs）
N ≥ 5  或  M ≥ 7   →  側欄（sidebar）
```

**我們現在 N = 6、M = 8 → 側欄。**
（六頁：輸入方案 / 外觀 / 文字 / 方案市集 / 連網 / 進階；最長是外觀的 8 項。）

**這個判準要寫死**：日後刪到 4 頁以下才可以改成分頁，不能因為「看起來比較清爽」就改。
理由：分頁在超過 5 個之後會換行或捲動，而換行的分頁列是最難用的一種導覽 ——
使用者永遠不確定自己有沒有看完全部。

**尺寸**：

| 項目 | 值 | 理由 |
|---|---|---|
| 視窗預設 | 780 × 560 pt | |
| 視窗最小 | 660 × 460 pt | 側欄 200 + 內容 440 + 邊距 |
| 側欄寬 | 200 pt 固定 | 不可拖曳。可拖曳的側欄只會讓四端截圖對不起來 |
| 內容欄最小 | 440 pt | |
| 內容欄最大 | 640 pt | 超過就置中留白。一行中文超過 40 字眼睛回不到行首（§3.2 規則 2） |

**側欄內容**：六個分頁 + 最底下一個**狀態區**（「● 可以打字」「離線」）。
狀態放側欄底部是刻意的：它在每一頁都看得到，而使用者最常問的兩個問題就是這兩個。

⚠ **「進階」頁只放四類東西**：修復（重新部署）、匯入匯出、介面語言、診斷。
想放第五類的時候，那代表分類本身要重做，不是進階要變大。
（三家對照品都有一個叫「高級」的無底洞，搜狗的甚至裝進了桌面寵物。）

### 5.2 行動端

- **兩層。第二層是終點。** 例外只有市集與換鍵（§4.5）。
- 左右邊距 s6（20dp），內容捲動，`systemBars` 的 inset 由最外層統一讓開一次
  （targetSdk 35 起強制 edge-to-edge，每一頁各自處理必漏）。
- **首頁四列一張卡**：把 17 個設定項收成四個問題 ——
  **用哪種鍵盤 · 長什麼樣 · 按起來什麼感覺 · 打出來是什麼字**。
  分類的依據不是技術歸屬，是**使用者當下腦中的那句話**。
- **「隨手試一下」是首頁的一部分。** 打出第一個字不該需要離開 App、
  去找一個聊天室、再點一個輸入框。而且**打壞也沒關係**。

### 5.3 桌面與行動的頁數差異

| 頁 | id | 行動 | 桌面 | 為什麼 |
|---|---|---|---|---|
| 輸入方案 | `schemas` | 現在叫「鍵盤」，**建議改叫「打字方式」**（見下） | ✅ | 桌面沒有軟鍵盤可選，要選的是方案 |
| 外觀 | `appearance` | ✅ | ✅ | 桌面只管候選窗 |
| 手感 | `feel` | ✅ | ❌ **整頁拿掉** | 震動、按鍵音、長按延遲都是軟鍵盤專屬 |
| 文字 | `text` | ✅ | ✅ | |
| 自己加的詞 | `dictionary` | ❌ 未實作 | ✅ 已上架 | 格式已用真的 librime 驗過（`settings-model.md` §5） |
| 方案市集 | `store` | ✅ | ✅ | |
| 連網 | `network` | ✅ | ✅ | |
| 進階 | `advanced` | ✅ | ✅ | |

**權威是 `docs/settings-model.md` §1**（頁的 id 與存在與否）。上面這張表只是把它抄過來，
再多加一欄「為什麼」。**兩張表不一致的時候以那一張為準**，並回來修這一張。

> **一個提案：行動端的「鍵盤」改叫「打字方式」。**
> 理由是它與同一屏的「外觀」會被混淆 —— 使用者以為「鍵盤」是調鍵盤長相的地方，
> 而它其實是選方案的地方。桌面端叫「輸入方案」，副標已經寫「你要用哪一種打字方式」，
> 也就是兩端都已經承認**「打字方式」才是白話**。
> **這需要 Android 端改 `home_keyboard` 這一個字串（三個語系）。**
> 我不動別人的路徑，所以由 Android 端決定要不要採納。
> 不採納也可以，但那時請把桌面端的副標一起改回去 —— 兩端不要各講各的。

### 5.4 響應式

| 寬度 | 版面 |
|---|---|
| < 600 dp | 行動端單欄 |
| 600–840 dp（平板直向、桌面小視窗） | 單欄，但內容置中並限寬 640 |
| > 840 dp | 側欄 + 內容欄 |

**規則：斷點只有兩個，而且切換的是版面，不是內容。**
任何一個尺寸下**都看得到全部功能** —— 不得因為視窗小就藏掉某一頁。

## 6. 文案規則

> **這是這個產品最關鍵的一節。**
> 使用者的原話是「你這個第一屏 99% 的人看不懂」，而問題不是選項太多，
> 是每一個選項都用**實作的詞**在講話。

### 6.1 三條硬規則

1. **每一個設定項都必須有一句白話，說它會改變什麼。**
   這句話由型別強制存在（macOS 端的 `blurb` 不是 Optional）。**沒有白話就不該上畫面。**
2. **不得把 YAML 欄位名或任何內部識別字搬到畫面上。**
3. **不得只重述標題。** 「繁體字還是簡體字」配上「設定繁體或簡體」等於沒寫。

### 6.2 詞彙對照表（規範性）

**這張表是防止「把 YAML 欄位名搬上畫面」最有效的一件工具。**
左邊一個都不准出現在使用者看得到的字串裡（診斷區塊除外）。

| 不要說 | 要說 |
|---|---|
| `schema_list` / schema / schema id | **打字方式**（頁標題可用「輸入方案」，但同一屏必須有白話副標） |
| `page_size` | 一次顯示幾個字 |
| `simplification` | 繁體字還是簡體字 |
| `ascii_punct` | 逗號句號用哪一種 |
| `full_shape` | 英文字母和數字的寬度 |
| deploy / 部署 / 重新部署 | **重新整理字詞** |
| 候選 / 候選字 / candidate | **選字**（「選字的那個小窗」） |
| preedit / 編碼串 | 你正在打的拼音 |
| commit / 上屏 | 打出來 / 送出去 |
| 詞庫 / 碼表 / dict / userdb | **你自己加的詞** |
| layout / layer / layout id / layer id | **鍵盤排列** / 用那一層自己的名字（「符號」「數字」「英文」） |
| remap | **換鍵**（動作說成「把兩顆鍵對調」） |
| 索引 / index | 可以下載的清單 |
| session / IMK / TSF / langid / librime | —（只准出現在診斷區塊） |
| 配置 / 設定檔 / custom.yaml | 設定 |
| 導入 / 導表 | 匯入 |

### 6.3 一句白話的配方

```
[做了會怎樣]。[什麼時候該用，或什麼時候不該用]。
```

- **最多兩句**，中文 ≤ 40 字，英文 ≤ 90 字元。
- **不得**用「設定…」「配置…」「開啟／關閉此選項」開頭。
- **不得**用條件句堆疊（「若…則…否則…」）。使用者不是在讀規格。
- **可以舉例，而且舉例通常比解釋好**：
  - ✅「中文標點是『，。』，英文標點是『, .』。寫程式的人通常要英文的。」
  - ❌「控制標點符號的全形／半形轉換行為。」
- **可以承認一件事很少用**：
  - ✅「全形的 A 和『中』一樣寬。排版對齊時偶爾會用到，平常用一般寬度。」
  - 這比假裝每個設定都很重要誠實，也讓使用者知道可以跳過。

### 6.4 標題、現值、說明的分工

| | 回答什麼 | 長度 |
|---|---|---|
| **標題** | 這是什麼 | 一行，不得折行（§3.2 規則 3） |
| **現值** | 現在是什麼 | 最多兩行，寬度 ≤ 該列一半 |
| **說明** | 改了會怎樣 | 最多兩句 |

**第一層只有標題 + 現值；第二層才有說明。**（§4.5）

### 6.5 誠實條：做不到的事要說出來

**RIME 的 `simplification` 是單向的（繁 → 簡）。**
所以「繁體輸入模式 + 只裝了簡體方案」的組合，字集**仍然是簡體**。

**介面上不得宣稱做得到。** 該做的是在「文字」頁放一條誠實條：

```
ⓘ 這個打字方式只有簡體字。要打繁體字，請改用「注音 · 臺灣正體」。
  [ 去換打字方式 ]
```

**這個形狀可以複用**：凡是「使用者選了 A，但物理上做不到」的情況，
一律用「說明現況 + 指出可行的路 + 一顆直達按鈕」，**不要把控制項灰掉了事**（D1）。

### 6.6 動作按鈕怎麼命名

- **寫動詞 + 受詞，不寫「確定」。** 「打開系統設定」「下載」「複製」「對調」「全部還原」。
- **進行中改成進行式，而且保持同一顆按鈕**：「下載」→「下載中…」。
  不要換成另一顆按鈕（位置一變使用者會以為自己按錯了）。
- **不要用「應用」「套用」**。設定應該立刻生效；需要「套用」的東西代表模型有問題。
  唯一例外是**需要重新部署**的那幾項，而那時要說的是「重新整理字詞」不是「套用」。

### 6.7 機器檢查得到的部分

禁用字分兩層，因為「一律禁止」會誤傷（`候選字` 是每一家中文輸入法設定頁上都有的詞，
禁掉它反而會讓四端各自發明譯法）。

#### 第一層：硬禁（出現就是紅，沒有例外）

引擎的內部識別字、ABI 函式名、除錯標記。**這些出現在使用者看得到的地方一律是 bug。**

```
rs_*           所有 ABI 函式名（rs_schema_list、rs_deploy、rs_set_option…）
schema_list    page_size    simplification    ascii_punct    full_shape    half_shape
speller        translator   segmentor         processor      prism         opencc
stabledb       db_class     table_translator  user_dict      custom_phrase
preedit        langid       rime_shell        librime        applicationId  namespace
STUB           TODO         FIXME             ⟦…⟧            任何 schema／layout／layer／bundle id
```

#### 第二層：需要白話配對（可以出現，但有條件）

| 詞 | 條件 |
|---|---|
| 候選 / 候選字 | **四端必須用同一個譯法。** 本規範選「選字」（macOS 端的頁副標已經是「選字的那個小窗」）。若要保留「候選字」，那就四端全部保留，**不可以一個檔案裡兩種都用** |
| 部署 | 一律改成「重新整理字詞」。使用者看得到的地方**不留**「部署」 |
| 配置 / 設定檔 | 改成「設定」；指一個檔案時說「設定檔」可以，但要說清楚是誰的 |
| 上屏 | 改成「打出來」或「送出去」 |
| 碼表 / 詞庫 | 改成「你自己加的詞」；指第三方的東西時可以說「詞庫」，但同一屏要有白話 |

**規則：第二層的每一個詞，同一屏裡必須至少有一句不用它也說得通的話。**
這一條靠人看，但「四端譯法一致」那一半靠機器（比對四端的字串表）。

#### 掃描範圍（每一端自己宣告，而且**必須斷言範圍非空**）

| 端 | 掃什麼 | 現況基準 | 例外（逐條列進允許清單） |
|---|---|---|---|
| Android | `android/app/src/main/res/values*/strings*.xml` | **9 個檔案、1413 條字串** | `diag_` 前綴的字串（診斷回報載荷） |
| macOS | `SettingsCatalog.swift` 的 `T(...)`、`Localized.swift` | **104 條 `T(...)`** | `diagnosticsNote` 以外的診斷字串 |
| Windows | 由 Windows 端宣告 | — | — |
| iOS | 由 iOS 端宣告 | — | — |

「現況基準」那一欄是 **2026-08-09 實際掃出來的數字**，寫進腳本當作 `N`／`M` 的下界。
數字比它小 → 代表範圍寫錯了 → **紅**。

⚠ **這個掃描器最可能的失效方式，是掃描範圍寫錯、掃到零個檔案、然後全綠。**
本專案的產品識別碼守門腳本正是這樣在六項全錯的情況下 6/6 全綠的
（原因：`find` 的範圍不含放那六項的目錄）。所以掃描器**必須**：

- 斷言掃到的檔案數 ≥ N、字串數 ≥ M；
- 允許清單裡的每一項都要指到存在的字串，指不到就紅
  （允許清單不可以活得比它的對象久）；
- 附一個植入違規的反向測試 —— 把 `page_size` 塞進一個字串，確認會紅。

#### 現況：我已經用這份表掃過一次

**掃描是唯讀的、沒有進版控，用的是上面那份表的一個子集**
（`rs_*`／`schema_list`／`librime`… 等 24 個西文詞 + 6 個中文詞；
`STUB`／`TODO`／`FIXME` 我沒有放進那一次的掃描器，但下面第 2 條它靠 `librime` 一樣被抓到）。
結果（2026-08-09，`design` 分支的樹）：

| 端 | 範圍 | 第一層違規 | 第二層待統一 |
|---|---|---|---|
| Android | 9 檔 / 1413 條 | **2 條字串**（三語系各一份 = 6 個條目） | 「候選字」11 處、「上屏」2 處、「部署」1 處、「配置」1 處 |
| macOS | `SettingsCatalog.swift` 104 條 `T(...)` | 0 | 「候選字」3 處 |

**第一層那兩條，逐字列出來**（都在 `values*/strings.xml`）：

| 字串 id | 內容 | 問題 |
|---|---|---|
| `keyboard_no_schema` | 「尚無可用方案（**rs_schema_list** 返回空）」 | **ABI 函式名直接印在使用者畫面上。** 這是最嚴重的一條，而且它是「一個方案都沒有」時唯一會看到的字 —— 正好是使用者最無助的時刻 |
| `keyboard_stub_notice` | 「**⟦STUB⟧** 未接 **librime**，候選字為假資料」 | 開發期的佔位訊息走了使用者字串資源。它平常不會出現，但「平常不會出現」正是它一直沒被發現的原因 |

**第二層裡最該先修的兩條**（它們雖然只踩到第二層，但問題比詞彙統一嚴重）：

| 字串 id | 內容 | 問題 |
|---|---|---|
| `remap_intro` | 「選同一層裡的兩個鍵交換位置…標著 **a** 的鍵搬到 **s** 的格子之後，按下去**上屏**的仍然是 a…」 | 用 key id 講解，而且講的是實作而不是效果。§7.7 整頁重做之後這一句可以直接刪掉 |
| `store_unverified` | 「…它沒有經過打包端的**部署**驗證，導入後有較高機率**整理字詞**失敗」 | **同一句話裡「部署」與「整理字詞」兩個講法並存** —— 使用者會以為那是兩件事 |

⚠ **這幾條由 Android 端修，不是我改的** —— `android/` 不是我的路徑。
列在這裡是為了證明**這條檢查值得寫**：它第一次跑就抓到真的東西，
而 `rs_schema_list` 那一條已經在出貨的 APK 裡。

## 8. 引導（第一次打開）

不是一頁，是**三步，而且每一步都只問一件事**。

```
第 1 步  這是什麼 + 離線是預設
   ┌────────────────────────────────┐
   │ LuminaKey                  t1  │
   │ 一個不連網的中文輸入法。   t3  │
   │                                │
   │ · 預設完全離線，一個封包   t5  │
   │   都不會送出去。               │
   │ · 要不要連網由你決定，而且     │
   │   連過哪裡你都看得到。         │
   │ · 不需要帳號。                 │
   │  ┌──────────────────────────┐  │
   │  │        開始              │  │
   │  └──────────────────────────┘  │
   └────────────────────────────────┘

第 2 步  在系統設定裡打開它
第 3 步  把它選成現在用的輸入法
```

⚠ **每一步的「完成」判定必須查系統狀態，不得記自己的旗標。**
語燕正是這樣困住使用者的：從系統設定先設好之後，它的精靈仍然停在第 3 步，
一定要從它自己的按鈕再走一次才會過關。

⚠ **不得有「跳過」。** Trime 的精靈有 SKIP，按下去之後 IME 進入崩潰迴圈，
而崩的是 `ColorManager`，錯誤訊息對使用者毫無意義。
我們的第 2、3 步是**系統層級的操作**，沒做就是不能打字 —— 跳過它等於讓使用者
帶著一個壞掉的東西離開。**做得到的是「稍後再說」，但那要退回第一屏的
「還不能打字」狀態卡，不是進到一個假裝一切正常的設定頁。**

### 12.1 前提：為什麼是純 Win32（這條不要試圖推翻）

理由寫在 `windows/service/settings_window.h` 的檔頭，這裡只複述結論與**它對設計的約束**：

| 被排除的 | 為什麼 |
|---|---|
| Electron / WebView2 | 打包或相依於 Chromium。**離線定位要能被外人用 `dumpbin /imports` 驗證**，塞一個瀏覽器引擎進來，那句話就永遠不可能成立 |
| WinUI 3 / XAML Islands | 需要 Windows App SDK 的執行階段相依，且與貫穿全案的 `/MT` 靜態 CRT 打架 |
| WPF / WinForms | 需要 .NET 執行期 |
| 本機 HTTP + 系統瀏覽器 | 會開 socket。為了設定介面讓服務進程監聽一個連接埠，等於親手推翻自己的主張 |

**對設計的約束（這一節其餘各段都是它的推論）：**

1. **沒有宣告式版面。** 每一個矩形要自己算 —— 所以版面必須抽成**純函式**，
   否則它在 Ubuntu 上驗不到（§12.12 的 W19／W20 靠這條）。
2. **系統控制項的外觀是 comctl32 v6 給的，改不了。** 圓角改不了、配色改不了、
   內距改不了。
3. **深色模式不存在。** Win32 沒有這個概念（§12.7）。
4. **無障礙是控制項自帶的。** 一旦 owner-draw，MSAA 的角色與狀態就**跟著消失**，
   而且沒有便宜的補救（§12.5 的判準整個建立在這條上）。

### 12.3 單位：`pt` → DIP → 實體像素

**規範裡桌面欄的 `pt`，在 Windows 上一律讀作 DIP（device-independent pixel，96 DPI 下 1 DIP = 1 px）。**
**不是**排版學的點（1/72 吋）。三條互相獨立的佐證：

1. §5.1 的視窗最小值是 660×460 `pt`，而現況程式碼寫的就是 `660 * dpi_scale_` px（`:523`）。
2. §3.2 的 `t3` 列標題是 13 `pt`。13 DIP ≈ 9.75 排版點，正好是 Windows UI 的慣用字級（Segoe UI 9pt）；
   若讀作排版點則是 17 px，對一列的標題太大。
3. §3.6 的桌面點擊目標最小 28 `pt`。28 px 落在 Windows 的 24–32 px 建議區間內；37 px 不是。

**換算（規範性）：**

```
px = MulDiv(dip, dpi, 96)          // 整數，四捨五入，這是 Win32 的既有慣用法
lfHeight = -MulDiv(size_dip, dpi, 96)   // 負值 = 字元高度，不是儲存格高度
```

⚠ **不得用 `static_cast<int>(dip * dpi_scale_)`**（現況 `:539`）。
它無條件捨去，150%／175% 下每一項各少 0–1 px，而**誤差沿著版面累積** ——
症狀是「高 DPI 下右邊那一欄擠在一起」，而沒有任何一行程式碼看起來是錯的。
`MulDiv` 用 64 位元中間值且四捨五入，是唯一該用的那個。

**`dpi` 從哪裡來：**

| 表面 | 取法 |
|---|---|
| 設定視窗 | `GetDpiForWindow(hwnd)`，並在 `WM_DPICHANGED` 更新 |
| 候選窗 | 插入點所在螢幕的 `GetDpiForMonitor`（`cand_window.cc:198–216` 已經是對的，照抄） |
| 懸浮狀態列 | 它自己所在螢幕；`WM_DPICHANGED` 重算 |

**高 DPI 下的三條硬規則：**

1. **`WM_DPICHANGED` 必須處理。** 進程已經是 per-monitor-v2，所以系統**會**送這則訊息；
   不處理的結果不是「維持原樣」，是**版面與系統的期待脫節**。
   處理內容：更新 `dpi_`、**重建所有字型**（字型是像素單位的，不重建就是模糊或錯大小）、
   重建所有筆刷／畫筆、`SetWindowPos` 到 `lParam` 給的建議矩形、`LayoutUi()`、
   `RedrawWindow(..., RDW_INVALIDATE | RDW_ALLCHILDREN | RDW_UPDATENOW)`。
2. **每一個 top-level 視窗各自算自己的 DPI。** 設定視窗與候選窗可能在不同螢幕上。
   ⚠ 子控制項**不會**各自收到 `WM_DPICHANGED`，一律由父視窗重新配置。
3. **不要在版面計算裡用 `GetSystemMetrics`**，用 `GetSystemMetricsForDpi`。
   前者回的是系統 DPI 的值，在第二顆螢幕上是錯的。

### 12.4 版面：側欄式，逐頁

#### 12.4.1 為什麼是側欄（判準吃的是產品的頁數，不是某一端實作了幾頁）

§5.1 的判準是 `N ≤ 4 且 M ≤ 6 → 分頁；N ≥ 5 或 M ≥ 7 → 側欄`。
**⚠ 這裡有一個很容易得到相反答案的陷阱：**Windows 目前只實作了 4 頁，
照著數會得到「分頁」—— 而那正是現況（`WC_TABCONTROLW`）。

**判準吃的是產品的頁數。** 桌面端是 **7 頁**（§5.3，2026-08-09 由 dictfix 補上「自己加的詞」）：
輸入方案／外觀／文字／自己加的詞／方案市集／連網／進階。`N = 7 ≥ 5` → **側欄**。

理由不只是照規矩：§11 給 Windows 的建議本來就是「**直接照 §7.2 + §5.1 做，不要先做一版再改**」。
按今天的 4 頁做分頁，等市集／連網／自己加的詞上線就要整個重做，
而那三頁上線是**已經排定的**（`product-gaps.md` §5.2）。

**側欄上只列已經實作的頁。** §2-D1：「做不到就整頁／整項拿掉」，
現況的註解（`:452–454`）也已經是這個判斷（「空的一頁比沒有那一頁更難理解」）。
一頁要出現在側欄上的條件：**它上面每一顆控制項都真的做了它宣稱的事**（§2-D2）。

#### 12.4.2 幾何（DIP；px = `MulDiv(dip, dpi, 96)`）

```
┌─ 200 ─┬────────────── 內容區 ──────────────┐
│       │        ← content_x                 │
│ 側欄  │   ┌── content_w ──┐                │
│       │   │  內容欄        │                │
│       │   └───────────────┘                │
├───────┤                                    │
│ 狀態區│                                    │
└───────┴────────────────────────────────────┘
```

| 項目 | 值（DIP） | 來源 |
|---|---|---|
| 視窗預設 | 780 × 560 | §5.1 |
| 視窗最小 | 660 × 460 | §5.1（`WM_GETMINMAXINFO` 強制，不是只設初始大小） |
| 側欄寬 | **200 固定** | §5.1「不可拖曳」→ **不得**用 `WC_SPLITTER` 或自製分隔條 |
| 側欄左右內距 | 12（s5） | §3.1 桌面欄 |
| 側欄項高 | 36 | ≥ §3.6 的 28 最小點擊目標 |
| 側欄項間距 | 4（s2） | §3.1 |
| 側欄狀態區高 | 64 | 兩行 t5 + 上下 12 |
| 內容欄上下內距 | 32（s8） | §3.1 |
| 內容欄左右內距 | 20（s7） | §3.1 |

```
avail      = W - 200
content_w  = clamp(avail - 2*20, 440, 640)
content_x  = 200 + (avail - content_w) / 2      // 置中；W > 840 時兩側留白
```

驗算：`W=780 → content_w=540, content_x=220`；`W=660 → content_w=440, content_x=210`
（最小尺寸下左右內距被壓到 10，這是刻意的：內容欄的 440 下界優先於邊距）；
`W=1000 → content_w=640, content_x=280`。**這三組數字寫進單元測試**（W19）。

### 12.5 元件：哪些用系統的、哪些自己畫

#### 12.5.1 判準（規範性，只有一條）

> **只有在系統控制項無法表達規範要求的某個狀態時，才 owner-draw。
> 外觀不夠好看不是理由。**

理由是無障礙，不是省事。Win32 的 owner-draw 會**同時**拿走兩樣東西：

* **MSAA／UIA 的角色與狀態。** `BS_OWNERDRAW`（`0x0B`）與 `BS_AUTOCHECKBOX`（`0x03`）
  **互斥** —— 它們都佔 `BS_TYPEMASK` 的低 4 位元。也就是說一顆 owner-draw 的核取方塊
  **不可能同時是核取方塊**：自動切換沒了，`STATE_SYSTEM_CHECKED` 也沒了，
  螢幕閱讀器會念成「按鈕」而不是「核取方塊，已勾選」。
  這正是 `docs/accessibility.md` 抓到的「念得出名字但輕點兩下什麼都不會發生」的同一族。
* **高對比佈景的自動適配。** 系統控制項在高對比模式下自己會變；自繪的不會（§12.7.4）。

補救要寫一份 UIA provider（`IRawElementProviderSimple` + `IToggleProvider`…）。
那是可以做的，但**每多一個自繪控制項就多一份**，而本節的清單刻意壓到最短就是為了這個。

#### 12.5.2 用系統控制項的（不要自己畫）

| 規範元件 | Win32 | 為什麼夠用 |
|---|---|---|
| 開關（§4.1） | `BUTTON` + `BS_AUTOCHECKBOX \| BS_RIGHTBUTTON` | Win32 的原生布林承載體就是核取方塊。§9 的規則是「長得像該平台的原生控制項比長得像另外三端重要」。`BS_RIGHTBUTTON` 把方塊移到**右邊**，滿足 §4.1「開關在右、標題說明在左」 |

| 一般按鈕 | `BUTTON` + `BS_PUSHBUTTON` | §3.3：「按鈕的圓角跟平台走，不跟我們走」 |

⚠ **「跟著○○」永遠是單選群組的第一格**（§4.2）。
⚠ **不得用 `CBS_DROPDOWNLIST`**（現況四處）。§4.4：下拉只給「≥ 7 個選項」用，
而現況四個下拉分別是 3／3／5／5 個 → 全部應為單選群組。
唯一真正的下拉是「預設方案」（數量隨資料變），它走 §12.5.3 的自繪彈出清單 ——
因為系統 ComboBox 的下拉鈕與外框在深色下是淺色的，改不掉（§12.7.3）。

其餘全部用系統控制項。

#### 12.6.4 三條自繪的硬規則

1. **焦點環只在鍵盤使用時畫。** 處理 `WM_UPDATEUISTATE`，`UISF_HIDEFOCUS` 被設起來時
   不畫焦點環。滑鼠使用者身上到處是框，是 Win32 自繪最常見的破綻。
2. **不要用 `DrawFocusRect`。** 它是 XOR 的點線框，在我們的色票上會變成不可預測的顏色。
   自己畫 2 DIP 的圓角矩形，圓角 = 元件圓角 + 2（§3.6）。
3. **雙緩衝。** 每一個自繪表面都照 `cand_window.cc:258–262` 的作法
   （`CreateCompatibleDC` + `CreateCompatibleBitmap` + 最後 `BitBlt`），
   並且 `WM_ERASEBKGND` 回 1。少了它，捲動清單會閃。

### 12.7 深色模式

**Win32 沒有深色模式。** 這一段把「做得到」與「做不到」分開寫，因為兩者的界線
決定了 §12.5.3 那張表的長度。

#### 12.7.1 做得到

| 項目 | 機制 | 備註 |
|---|---|---|
| **標題列與外框** | `DwmSetWindowAttribute(hwnd, DWMWA_USE_IMMERSIVE_DARK_MODE, &BOOL_TRUE, sizeof(BOOL))` | 屬性值 **20**（Win10 1903+／Win11，已公開文件）。Win10 1809 是 **19**。作法：先試 20，回傳失敗再試 19，再失敗就放著（淺色標題列 + 深色內容，難看但不會壞） |
| **視窗底色** | 自己在 `WM_ERASEBKGND`／`WM_PAINT` 畫，`WNDCLASS.hbrBackground` 設 `nullptr` | 現況是 `COLOR_BTNFACE + 1`（`:197`），要拿掉 |
| **`STATIC` 的文字與底** | `WM_CTLCOLORSTATIC`：`SetTextColor` + `SetBkColor` + 回傳快取的背景筆刷 | ⚠ **筆刷要快取**，不要每次訊息 `CreateSolidBrush` —— 那是 GDI 物件洩漏，症狀是「開幾小時之後畫面開始畫不出來」 |
| **核取方塊／單選鈕的文字與底** | 同上（它們送的也是 `WM_CTLCOLORSTATIC`） | **只有文字與底**，方塊本身見 §12.7.3 |
| **唯讀 `EDIT` 的文字與底** | `WM_CTLCOLORSTATIC`（唯讀的送這個，不是 `WM_CTLCOLOREDIT`） | |
| **我們自己畫的每一塊** | §12.6 的兩張表 | |
| **偵測系統偏好** | 讀 `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` 的 `AppsUseLightTheme`（DWORD，`0` = 深色）。鍵不存在 → 視為淺色（Win10 1803 前） | |
| **跟著系統即時切換** | `WM_SETTINGCHANGE` 且 `lParam` 字串 == `L"ImmersiveColorSet"` → 重讀登錄檔 → 若變了就重建筆刷／畫筆 → `DwmSetWindowAttribute` 再設一次 → `RedrawWindow(..., RDW_INVALIDATE \| RDW_ALLCHILDREN \| RDW_UPDATENOW)` | ⚠ 標題列不一定跟著重畫，補一發 `SetWindowPos(..., SWP_FRAMECHANGED \| SWP_NOMOVE \| SWP_NOSIZE \| SWP_NOZORDER)` |

#### 12.7.2 三態，不是兩態

§3.5 第 1 條：「`followSystem` 是預設，而且是三態的第一態」。
所以設定裡是**跟著系統／淺色／深色**的單選群組，不是一個開關。
只有兩態的話，使用者按過一次就回不到「讓系統決定」。

#### 12.7.3 做不到（在**不使用未公開 API** 的前提下）

| 項目 | 為什麼 |
|---|---|
| **核取方塊／單選鈕的方塊本身** | 啟用視覺樣式後由 uxtheme 畫，永遠是淺色佈景的字形。`WM_CTLCOLOR*` 只影響文字與底 |
| **`ComboBox` 的下拉鈕與外框** | 同上。`CBS_OWNERDRAWFIXED` 只能畫**項目**，鈕與框仍是系統畫的 |
| **系統捲軸** | ListView／EDIT 的捲軸由系統畫 |
| **`WC_TABCONTROLW` 的分頁片** | 同上（不過我們改成側欄，這一格自然消失） |
| **`MessageBoxW`** | 整個對話框由系統畫（不過 §12.5.3 已經要求改成自己的對話框） |
| **系統匣的快顯選單** | `TrackPopupMenu` 的配色跟系統走 |

**裁決：禁止使用 `uxtheme.dll` 的未公開序數 API**
（`SetPreferredAppMode` / `AllowDarkModeForWindow` / `ShouldAppsUseDarkMode` /
`RefreshImmersiveColorPolicyState`，它們沒有名字，只有序數 132／133／135／104）。

理由與這個專案的定位直接相關，不是潔癖：
1. **審計。** 一個外人讀到 `GetProcAddress(uxtheme, MAKEINTRESOURCEA(135))` 看不出它在做什麼。
   我們要求別人相信「這支程式不連網」，靠的就是「每一個匯入都解釋得清楚」。
2. **序數會變。** 它們不在任何契約裡，一次 Windows 更新就可能挪位，
   而失敗的樣子是**呼叫到別的函式**，不是回傳錯誤。
3. 它換到的東西很小 —— 見上表：方塊字形、捲軸、下拉鈕。

**因此：凡是在深色下會露出系統淺色繪製的控制項，要嘛 owner-draw，要嘛不要用它。**
§12.5.3 那張表就是這條規則推出來的，不是照外觀挑的。
留下來的兩處已知瑕疵（**核取方塊與單選鈕的方塊字形**、**ListView 的捲軸**）
是**刻意接受**的，寫在這裡是為了讓它不要被當成 bug 反覆回報。

#### 12.7.4 高對比是第三種模式，不是深色的一種

`SystemParametersInfoW(SPI_GETHIGHCONTRAST)` 回報開啟時：
**整份色票停用，改走 `GetSysColor()`**（`COLOR_WINDOW`、`COLOR_WINDOWTEXT`、
`COLOR_HIGHLIGHT`、`COLOR_HIGHLIGHTTEXT`、`COLOR_GRAYTEXT`、`COLOR_BTNFACE`）。

這與 §2-F4「深色模式只換色票，不動版面」一致 —— 高對比也只是**第三份色票**。
⚠ 而且它是必要的：使用者開高對比是因為他**看不清楚**，這時我們的青瓷綠不是幫忙。
`WM_THEMECHANGED` 與 `WM_SETTINGCHANGE`（`SPI_SETHIGHCONTRAST`）時重讀。

### 12.8 字型

#### 12.8.1 現況違規

`settings_window.cc:428` 與 `cand_window.cc:28` 都用 `SPI_GETNONCLIENTMETRICS` 的
`lfMessageFont`。**§8.6.0 明文禁止**：「桌面端不得改用系統 UI 字型當預設。
`$system` 代號已經是那個意思，而走代號才能讓『主題指定了字體』與
『主題沒指定，用系統字體』是**同一條程式路徑**」。

⚠ **順帶一個現況的計算錯誤**：`:430` 把 `lfMessageFont.lfHeight` 再乘一次 `dpi_scale_`。
在 per-monitor-v2 進程裡，`SPI_GETNONCLIENTMETRICS` 回的是**系統 DPI** 的度量，
已經含一次縮放 —— 系統 DPI > 96 時這是**二次縮放**，字會過大。
（這一條是從 API 契約推的，**我沒有在真機上量過**；見 §12.13。）
改成走下面的解析順序之後這個問題自然消失，因為字級直接來自規範的 DIP 值。

#### 12.8.2 該用什麼

字級一律取規範的 `size`（§3.2 桌面欄：t1 22／t2 15／t3 13／t4 12／t5 11／t6 11 等寬），
`lfHeight = -MulDiv(size_dip, dpi, 96)`。
字體家族走 §8.4.1 的 `$system` 代號對照表：

| 用途 | 堆疊（§8.6.0 綁定） | Windows 解析順序 |
|---|---|---|
| 設定介面、狀態列 | `typography.fonts.ui`（`["$system"]`） | `Segoe UI Variable Text` → `Segoe UI` → `Tahoma` → `MS Shell Dlg 2` |
| 候選文字 | `typography.fonts.candidate` | 同上，再依 §8.4.2 的 `script_fallback` |
| 序號標籤 | `typography.fonts.label` | 同上 |
| 註解 | `typography.fonts.comment` | 同上 |
| 診斷（t6 等寬） | `$mono` | `Cascadia Mono` → `Consolas` → `Courier New` |

⚠ `$system` 的第一順位寫的是 **`Segoe UI Variable Text`**，不是 `Segoe UI Variable`。
後者是家族名，含 `Display`／`Text`／`Small` 三種視覺尺寸，
`CreateFontIndirectW` 拿家族名會挑到哪一個沒有保證。UI 內文要的是 `Text`。

**CJK 依 §8.4.2 的 `script_of(run)` 分支**（規範性，四端必須一致）：

| script | 順序 |
|---|---|
| `hant` | `Microsoft JhengHei UI` → `Microsoft JhengHei` → `MingLiU` |
| `hans` | `Microsoft YaHei UI` → `Microsoft YaHei` → `SimSun` |
| `jpan` | `Yu Gothic UI` → `Yu Gothic` → `MS UI Gothic` |
| `kore` | `Malgun Gothic` → `Gulim` |

⚠ §8.4.2 第 5 條：漢字本身不帶語言資訊，**依 `rs_status.is_simplified` 決定 `hant` / `hans`**。
四端必須用這一條，否則同一份主題在兩台電腦上顯示不同字形。

#### 12.8.3 字型不存在時的退化（這一段最容易做錯）

⚠ **`CreateFontIndirectW` 永遠不會失敗。**
`lfFaceName` 給一個不存在的字體，它回一個**有效的 HFONT**，然後 GDI
安靜地替你挑一個「相近」的字體。也就是說**回傳值不能拿來判斷字體在不在**。

**規範性的解析程序：**

```
for family in resolved_list:            # §8.6.0 綁定 + §8.4.2 的 script_fallback
    if FontExists(family):              # EnumFontFamiliesExW，比對 lfFaceName（不分大小寫）
        return CreateFontIndirectW(with family)
return CreateFontIndirectW(with lfFaceName = "")   # 交給 GDI 依 lfPitchAndFamily 挑
```

* `FontExists` 用 `EnumFontFamiliesExW`，`LOGFONTW.lfCharSet = DEFAULT_CHARSET`，
  在回呼裡比對 `lfFaceName`。**這是唯一可靠的存在性檢查。**
* 結果**要快取**。`EnumFontFamiliesExW` 每一次都會列舉整台機器的字體，
  放在 `WM_PAINT` 裡等於每一幀掃一次字體清單。
* 全部不存在時最後一格**留空字串**，不是硬塞 `Segoe UI` ——
  空字串下 GDI 依 `lfPitchAndFamily`（等寬用 `FIXED_PITCH \| FF_MODERN`）挑，
  在中文版 Windows 上挑出來的東西比我們猜的好。
* **逐字形 fallback：GDI 的 `TextOutW` 不做。** §8.4.2 已經規定了退化方式：
  「無法做逐字形 fallback 的渲染管線**應**退化為『用清單第一個成功載入的字體渲染整段』」。
  照做 —— **不要**為此引入 DirectWrite（多一組相依，而 §12.1 的整個論證就是在避免這件事）。
  漏字由 Windows 的 GDI font linking 兜底，那是系統行為，不是我們的選擇。

### 12.9 字串資源化與 §6.7 的掃描範圍宣告

#### 12.9.1 機制：自己的 catalog，**不是** `.rc` 的 `STRINGTABLE`

現況 85 個相異中文字面值散在 `settings_window.cc` 裡，只有繁體中文。
目標與另外兩端一致：**英／繁／簡三語**。

**建議：`windows/service/ui_strings.h` + `ui_strings.cc`**，
一個 `enum class UiString`、一個 `kCount`、每個語系一個 `const wchar_t* const [kCount]` 陣列，
取用一律 `UiText(UiString::kSchemasTitle)`。

**為什麼不用 `.rc` 的 `STRINGTABLE`：**

1. **§2-G2 要的「範圍非空」可以升級成編譯期保證。**
   `static_assert(std::size(kZhHant) == kUiStringCount)` 三份 ——
   少一條字串**編不過**，比任何掃描腳本都早、都硬。
   這正是 §2-B2 誇 macOS 的那種「型別強制」，在 C++ 裡的等價物。
2. **介面語言是使用者設定**（§5.1：「進階」頁的四類之一），不是執行緒的 UI 語言。
   `LoadStringW` 只認執行緒 UI 語言；要指定語系得走
   `FindResourceExW(RT_STRING, MAKEINTRESOURCE(id/16 + 1), langid)` 再自己剖 16 條一組的
   Pascal 字串塊 —— 為了一件本來很簡單的事寫一段很容易錯的碼。
3. **建置相依。** `.rc` 會把資源編譯器拉進建置。它遲早要來（系統匣圖示、應用程式資訊清單，
   見 `settings_window.cc:308–309`），但**字串不該等它**。
4. 掃描友善：一個檔案，一行一條，`grep` 得到，行數就是條數。

#### 12.9.2 §6.7 掃描範圍宣告（Windows 端，補上 §6.7 那張表的空格）

| 端 | 掃什麼 | 現況基準 | 例外（允許清單） |
|---|---|---|---|
| **Windows** | `windows/service/ui_strings.cc`（**唯一**允許出現使用者可見字串的檔案） | 見下 | `kDiag*` 開頭的識別字（§4.11 的診斷回報載荷，永遠英文、不在地化） |

**N／M 下界（寫死進腳本）：**

| 斷言 | 值 | 為什麼是這個數 |
|---|---|---|
| 掃到的檔案數 | **≥ 1** | catalog 只有一個檔案，所以這條退化成「檔案在不在」 |
| catalog 的條目數 | **≥ 80** | 現況相異中文字面值 85（§12.2 的量法）。取 80 是留給重新設計時的合併，**不是**放寬 —— 低於 80 代表搬漏了 |
| 每個語系的陣列長度 | **== `kUiStringCount`** | 編譯期 `static_assert`，三份都要 |

⚠ **只斷言下界是不夠的，這正是 §2-G 講的那個失效方式。**
所以再加一條**反方向**的檢查，它比計數強得多：

> **`windows/` 底下，除了 `ui_strings.cc` 之外，任何檔案都不得含有帶中日韓字元的
> 寬字串字面值。命中數必須是 0。**

這條把「掃描範圍寫錯 → 掃到零個 → 全綠」這個失效模式堵死了：範圍寫錯的話，
0 命中不再是「通過」，因為同時要斷言**掃到的原始檔數 ≥ 20**
（`windows/` 底下現有 `.cc`／`.h` 遠多於這個數）。

**反向測試（§2-G1，缺一不可）：**

| 檢查 | 植入什麼 | 預期 |
|---|---|---|
| 禁用字第一層 | 在 catalog 塞一條含 `page_size` 的字串 | 紅 |
| catalog 以外無字串 | 在 `settings_window.cc` 塞一句 `L"測試"` | 紅 |
| 範圍非空 | 把掃描路徑改成不存在的目錄 | 紅（**不是**零違規） |
| 語系齊備 | 從 `kEnUs` 陣列刪掉一條 | **編不過** |

#### 12.9.3 兩條字面規則

1. **`中`／`En`／`简`／`繁` 不進 catalog。**
   §8.12 規定這四個字面是**規範性、四端一致**的。進了 catalog 就會有人把
   簡體語系的「简」翻成「簡」，而那正是規範要避免的事。
   它們以字面直接寫在狀態列的繪製碼裡，並由 W10 斷言**不出現在 catalog**。
2. **診斷字串永遠英文，不進 catalog**（§4.11）。
   旁邊那句「這些數字是給我們看的，你不用懂」**要**進 catalog（它是介面文字）。

### 12.10 懸浮狀態列（新表面）

> 使用者原話：「小小一橫在右下角，可以拖動，上面可以快捷修改」（`product-gaps.md` §4.1）。

#### 12.10.1 ⚠ 它與規範 §8.12 的關係（先讀這一段）

**這不是 §8.12 的 `status_bar`。**

| | §8.12 `status_bar` | 本節的懸浮狀態列 |
|---|---|---|
| 住在哪 | **候選窗裡面**。§8.12 末句：「`follow_caret: false` 時狀態列仍然在候選窗內部，不是螢幕上的另一條帶子」 | 螢幕上的獨立 top-level 視窗 |
| 何時看得見 | 只有組字時（候選窗出現時） | **這個輸入法正在被使用時**（見 §12.10.6）。不是「一直都在」—— 2026-08-11 改的，被 Microsoft 的 IME 要求推翻 |
| 可否拖動 | 否 | 是，且記住位置 |
| 預設 | `show: false` | **預設開**（理由見下） |
| 規範地位 | 已規範 | **規範沒有這個表面** |

**共用的部分（規範性）：**

* **`source` 的字面必須沿用 §8.12**：第一格用 `input_mode`
  （`is_ascii_mode ? "En" : "中"`），第二格用 `variant`（`is_simplified ? 简 : 繁`）。
  **兩格都只顯示當前那一個**，**不得**在地化（§12.9.3）。

  ⚠ **2026-08-10 改過一次，改的理由值得留著。** 這裡原本規定第一格用
  `input_mode_pair`（`中`/`En` 兩態同時顯示，當前那一態用「當前態文字」色），
  依據是「只顯示一個字的話，『中』有兩種讀法（『現在是中文』還是
  『按下去變中文』），Android 被真機回報過」。使用者在真 Windows 上用過之後
  回報：「中/en 應該是現在是什麼輸入法就顯示什麼什麼輸入法，簡繁 就做得很好」。

  也就是說那個顧慮**同樣適用於第二格**，而第二格（只畫一個字）他讀得懂。
  真正的問題不是「一個字還是兩個字」，是**同一條狀態列上兩格用了兩種語彙**：
  深淺是**相對**的訊號（要兩個都看見、而且知道規則才解得開），
  只畫一個字是**絕對**的（看一眼就是答案）。讀法的歧義由「這一橫整條都是
  狀態指示、不是按鈕」這個一致性解決，不是由多畫一個字解決。

  §8.12 兩個 `source` 都是規範性的，所以這是**換 source**，不是違反規範。
  `input_mode_pair` 仍然存在，給主題作者用在候選窗裡的 `status_bar` 上。
* **空狀態必須整項略過**（§8.12 規範性）：`schema_name` 還沒載入完成時，那一格
  **完全不佔位置**，不得畫成一塊看不出用途的空白。
* **不得加圖示。** §8.12 末段記著一個**還沒關的缺口**：「`source` 全部是文字，沒有圖示」，
  並明寫「在補上之前，任何『一顆代表當前方案的小圖示』都是各端自己發明的，不要做」。
  四格純文字是可行的，**所以不必等那個缺口，但也不可以順手加圖示**。
* **兩個表面必須讀同一份 `rs_status` 快照。** 主題把 §8.12 的 `status_bar` 打開時，
  兩處會同時顯示同一組狀態 —— 那是允許的；**顯示不一致的值不允許**。

**規範所有權在 macOS 端**（`coordination.md` §2）。所以本節寫的是
**Windows 平台專屬的提案**，要不要進 `docs/theme-format.md` 由 macOS 端裁決 ——
已寫進 `coordination.md` §5。建議進規範，因為 macOS 選單列上那顆圖示是同一個問題的
另一半，兩端各自發明會長成兩個東西。

#### 12.10.2 為什麼預設是開的

⚠ **2026-08-11 整節重寫。前提過期了，而只改結論不改論證會讓下一個人
再推一次同樣的錯誤結論。** 舊版的論證與它為什麼不再成立，都留在下面。

**舊的論證（已過期）：**

> `product-gaps.md` §4.1.1 讀碼確認：`ascii_mode` 在整個 `windows/` 底下
> 只出現兩次，都是「回報狀態」，沒有任何一處設定它。三條可能的路全部
> 不通：Shift（TSF 不交付純修飾鍵）、語言列（`InitMenu` 回 `E_NOTIMPL`）、
> 系統匣（沒有中英那一項）。
>
> 也就是說：Windows 使用者要在句子中間打一個英文字，唯一的辦法是按
> Win+空白鍵把整個輸入法換掉。這一橫不是「多一個方便的入口」，它是
> **那個功能唯一的家**。預設關掉等於預設沒有中英切換。

**為什麼它不再成立：**

那三條路現在通了兩條，而且都不是這一輪才做的：

| 路 | 舊結論 | 現況 |
|---|---|---|
| **Ctrl + 空白鍵** | 「Shift 不通」（問的是 Shift，不是這一顆） | **通了。** `tsf/text_service.cc` 註冊了 `PreserveKey{VK_SPACE, TF_MOD_CONTROL}`;判斷在四端共用的 `common/hotkey_policy.cc`;`pipe_server.cc` 接得起來 |
| **系統匣** | 「沒有中英那一項」 | **有了。** 右鍵選單上「中文 / 英文」兩項，走 `Engine::SetAsciiModeAll()`。它在服務活著時**必然存在**，與有沒有宿主在用無關 |
| 語言列 | `InitMenu` 回 `E_NOTIMPL` | 不變（沒做，也不打算做 —— `GUID_LBI_INPUTMODE` 另開工單） |
| Shift 輕點 | TSF 不交付純修飾鍵 | **量到了，而那句話是假的。** CI run `31511075812`（sha `ca97498`）`logic-x64` 的「真的經過 TSF」那一步：在真的 `ActivateEx` 過的文字服務上經 `ITfKeystrokeMgr` 送一次左 Shift，`SHIFT_TRACE_LINES=1`，而多出來的那一行是 `OnTestKeyDown` 自己寫的（`vk=0x10 scan=0x2A keysym=0xFFE1 族=host-only 吃掉=0`）。**sink 收得到純修飾鍵，不需要低階鍵盤 hook**；`common/key_eat_policy.cc:120` 才是對的那一份。✅ **2026-08-12 已實作**（#89）：`common/shift_tap.cc` 的純函數狀態機，接在 `OnTestKeyDown` / `OnTestKeyUp`，`*eaten` 一律 FALSE；開關 `text.shiftTapToggle` 預設開。⚠ 「真實宿主的訊息迴圈會不會把 `VK_SHIFT` 送進 TSF」仍然只有真機驗得到（#48）。量法與跨端影響見 `docs/coordination.md` 的 `[2026-08-12] [winbar]` |

**新的論證：**

中英切換現在有三個家，而這一橫只是其中**最容易被發現**的那一個。
所以：

* **預設仍然是開的** —— 但理由變了。不是「否則就沒有中英切換」，
  而是「它是唯一一個看得見、而且點得到的入口」。使用者不會去讀說明，
  他會找一個看得到的東西點下去。
* **而它現在敢自己消失了**（§12.10.6）。那一橫不在的時候，鍵盤上那顆鍵
  與托盤那一格仍然在 —— 「那一橫不在」不再等於「沒辦法切中英文」。
* **所以那句文案必須說得出那顆鍵。** 使用者實機回報「我用 shift 切換
  中英文，但是他不變」，而他要的東西一直都在，缺的只是有人告訴他。
  `common/ui_strings.cc` 的 `kStatusBarBlurb` 現在寫著
  「在句子中間切中英文：Ctrl + 空白鍵，或點這一橫的第一格。」
  三個語系齊備，由 `tests/test_ui_strings.cc` 守著。

⚠ 使用者要關得掉（有人覺得礙眼）：設定裡一個開關。
**這一橫上不放 X** —— 一顆會讓它消失、而且不知道怎麼找回來的鈕，
會被誤點。這一條**不變**：自動隱藏與 X 不是同一件事，見 §12.10.6。

#### 12.10.3 視窗機制

| 項目 | 決定 | 理由 |
|---|---|---|
| 樣式 | `WS_POPUP`；`WS_EX_TOOLWINDOW \| WS_EX_TOPMOST \| WS_EX_NOACTIVATE` | `TOOLWINDOW` 讓它不出現在 Alt+Tab 與工作列；`NOACTIVATE` 讓點它不搶焦點 |
| `WM_MOUSEACTIVATE` | 回 `MA_NOACTIVATE` | 照 `cand_window.cc:158` 的既有作法。**搶焦點會讓使用者正在打字的輸入框失去插入點** —— 而「在句子中間切中英」正是這一橫存在的理由 |
| 方案清單怎麼彈 | **自繪的 top-level 小視窗，不是 `TrackPopupMenu`** | `TrackPopupMenu` 要先 `SetForegroundWindow` 才會在點外面時正常關閉（`settings_window.cc:358–360` 已經記著這件事），而那就是搶焦點。用自己的小窗 + 滑鼠捕捉 |
| 繪製 | 全自繪，雙緩衝，`WM_ERASEBKGND` 回 1 | §12.6.4 |
| 透明度 | **先不做。** 不用 `WS_EX_LAYERED` 的 alpha | §8.6.7.4 的精神：做不到就退化成不透明，而不透明本來就夠用 |

**拖動（規範性）：**

**不要**用 `WM_NCHITTEST` 回 `HTCAPTION`。那會讓整條都變成拖動區，四格就點不到了；
留一小塊「握把」又要使用者去找它。改成自己做：

```
WM_LBUTTONDOWN : 記下起點，SetCapture
WM_MOUSEMOVE   : 位移超過 (GetSystemMetrics(SM_CXDRAG), SM_CYDRAG) → 進入拖動
WM_LBUTTONUP   : ReleaseCapture
                 沒進入拖動 → 當作點擊那一格
                 進入過拖動 → 存位置，不觸發那一格
```

這讓「按住任何一格拖動」與「點一格」都成立，使用者不必知道握把在哪。
⚠ `SM_CXDRAG` 是使用者可調的，**不要寫死 4 px**。

**尺寸（DIP）：**

| 項目 | 值 |
|---|---|
| 高度 | **28**（= t4 字高 12 + 上下 padding 各 6 + 邊框 2）。同時滿足 §3.6 的 28 最小點擊目標 |
| 每格最小寬 | **28**（§3.6） |
| 格內左右內距 | 10（s4） |
| 格與格之間 | 6（s3） |
| 圓角 | 7（§3.3 的「中」，桌面欄） |
| 外框 | 1，`outline` 色 |

#### 12.10.4 四格（`product-gaps.md` §4.1.2 的建議，這裡定死行為）

| 格 | `source` | 顯示 | 點擊 | 空狀態 |
|---|---|---|---|---|
| 1 | `input_mode` | `是英數 ? En : 中`（**只有一個字**，理由見 §12.10.1） | `input_mode:toggle` | 不會空 |
| 2 | `variant` | `简` / `繁` / **整格不顯示**（三態，判定見下） | 送出偏好之後**向引擎回讀**，不樂觀寫入 | 引擎沒有回報字形 → **整格略過** |
| 3 | `schema_name` | 方案名 | **開自繪清單，不是循環切換**（預設四個方案，循環要按三下才回得來） | 名字為空 → **整格略過** |
| 4 | （§8.12 沒有這個 source） | 「設定」（**進 catalog，要在地化**） | 開設定視窗 | — |

**第 2 格的 `variant` 從哪裡來（規範性，四端一致）：**

```
zh_hans 為真                                → 简
zh_hant / zh_hant_hk / zh_hant_tw 任一為真   → 繁
四個都為假                                   → 整格不顯示
```

⚠ **`simplification` 不得用於判定。** 本專案打包的方案（luna_pinyin 家族、
bopomofo 家族）沒有這個開關，而 `rs_set_option` 對一個不存在的選項
**不會失敗** —— 它原樣記下、原樣回讀。用它判定等於把自己寫進去的偏好
當成引擎的狀態回報，而使用者實機回報的正是那件事：設定裡選了簡體、
這一格畫「简」、打出來是繁體。

`PlanVariant` 仍然要**設**它（第三方「簡入繁出」之類的方案靠它），
只是不再**讀**它。門面那一側新增了 `rs_status.variant`
（`RS_VARIANT_UNKNOWN / HANT / HANS`）;`rs_status.is_simplified` 保留但

⚠ **不要用「沒有那組 radio 時 fallback 到 `simplification`」補洞。**
純 `luna_pinyin` 的那組 radio **沒有 `reset:`**，而 librime 的

（emulator-5558 實測，`scripts/verify_variant_persistence.sh` 的情境 0b。）

⚠ **「整格不顯示」不是畫一塊空白**，沿用本表第 3 格「名字為空 → 整格
略過」的既有先例。

⚠ **這一格不得樂觀寫入**：點下去之後，在引擎回報新狀態之前不改變字面。

⚠ **殘留（明著寫出來，沒有解決）**：一個既沒有那組 radio、也沒有

⚠ **實測補充**：`shared/default.yaml` 的 `switcher/save_options` 列著

#### 12.10.5 位置的記憶、多螢幕、高 DPI

⚠ **不得只存螢幕座標。** 拔掉外接螢幕之後那個座標會落在螢幕外，
而症狀是「那一橫不見了」，使用者不會把兩件事聯想在一起。

**存什麼（規範性）：**

```
{ work_left, work_top, work_right, work_bottom }   // 存下當時那顆螢幕的工作區矩形
{ dx, dy }                                          // 相對工作區右下角的 DIP 偏移（正值 = 向左上）
```

**還原（規範性，三段回落）：**

1. 列舉螢幕，找工作區矩形與快照**完全相同**的那一顆 → 用它 + `dx/dy`。
2. 找不到 → **主螢幕**工作區的右下角 + 預設偏移 `dx = dy = 12`。
3. 無論走哪一條，**最後一律把視窗矩形夾進該螢幕的工作區**
   —— 沿用 §8.6.7.3 已經寫下的那條規則：「窗**必須**完整落在可用區內。
   先夾窗的尺寸，再擺位置 —— 位置的計算不得產生負的邊距」。

用**工作區**（`MONITORINFO.rcWork`）不是整個螢幕矩形：整個矩形會讓這一橫被工作列蓋住，
而 §8.6.7.3 已經註明那是實測會發生的事，不是理論問題。

⚠ **這三段全部是純函式。** 輸入是「快照 + 目前的螢幕清單」，輸出是一個矩形。
放進 `windows/common/`（與 `cand_layout.h` 同一個模式），**在 Ubuntu 上測得到，
不需要真的 Windows**。W20 就是靠這條。

**高 DPI：**這一橫是 top-level，per-monitor-v2 下拖到另一顆螢幕會收到 `WM_DPICHANGED`。
取 `lParam` 建議矩形的**位置**，尺寸自己依新 DPI 重算（它是固定 DIP 尺寸的小窗，
建議尺寸對它沒有意義），重建字型，重畫。

#### 12.10.6 什麼時候在、什麼時候不在（2026-08-11 新增，2026-08-14 大改）

⚠ **使用者實機回報：「怎麼就常駐了」。**

他**沒有**說「我不要這個東西」—— 這一橫是他自己要求的
（`product-gaps.md` §4.1：「小小一橫在右下角，可以拖動」）。要拿掉的只有
「他沒在用的時候還在」這一件事。

**規範（四端一致）：**

可見性由兩個輸入決定：

1. **使用者總開關**（`appearance.floatingBar`，預設開）。關 → 永遠不顯示，
   沒有例外。
2. **`in_use`：使用者此刻輸入焦點所在的那一條宿主執行緒上，啟用中的輸入法
   是不是我們。**

* **顯示**：1 且 2 → **立刻**顯示。
* **隱藏**：2 不再成立後，等 **3000 毫秒**才隱藏;期間恢復則**取消**待隱藏
  （不是延後）。
* **答不出來**：**維持現狀**（見下面那一格），不顯示也不隱藏、也不重新計時。
* **位置**：重新出現時回到使用者拖過的同一個位置，不重新定位。

⚠ 自動隱藏**不是**關閉。它不改變總開關的值，而且條件恢復時它自己回來。
⚠ 這一橫上仍然**不放 X**（§12.10.2 那一條不變）。
⚠ 每一端都必須有一個**與這一橫無關、而且在這個輸入法沒被使用時仍然
存在**的入口通往設定。Windows = 系統匣圖示（左鍵開設定）+ 開始選單捷徑;
macOS = 選單列項目;Android = 系統設定的輸入法項目 + app 圖示。

**⚠ 2 不是「有沒有人連著我們」（2026-08-14 推翻了原本那一句）**

原本第 2 條寫的是「這個輸入法目前有沒有被宿主使用（Windows：至少一條
TSF 連線活著）」，而焦點只是加強條件、**拿不到時一律視為「有」**
（fail-visible）。使用者實機回報（Windows 11，13 個進程載入了我們的 DLL）
三個症狀，三個是同一句話寫錯作用域的三個方向：

* **S1** 切到我們、還沒打字 → 那一橫**不在**（條件其實成立，而我們看不到
  它：activation 那條路上不開任何連線）。
* **S2** 打字時忽有忽無 → 焦點是**單一全域布林**，由「最後說話的那個宿主」
  寫，背景宿主一進場就把前景那個蓋掉。
* **S4** 已經切到別的輸入法 → 那一橫還自己冒出來（把**別人的**條件當成
  自己的：「有幾條連線開著」是一個沒有產品意義的量）。

⚠ **fail-visible 一併退場。** 它白紙黑字的理由是「焦點訊號在使用者打第一個
字之前根本不送」。那個前提在「切到我們的當下就建立在場訊號」之後就消失了
—— 留著它的意思會變成「不知道的時候顯示」，而 S4 正是不知道。

**怎麼算出 2：三個層次，不是三個選項**

1. **宿主提案。** 只有宿主自己知道「這條執行緒／這個 client 上啟用中的是不是
   我們」。Windows：`ITfInputProcessorProfileMgr` 是 per-thread、per-process
   的，服務端問不到別的進程 —— 所以宿主用**一條在場連線的生死**表達它
   （activation 開、deactivation 關），並在握手時報上 `(pid, tid)`。
   macOS / Android 的等價物由該端填，但**必須帶得出作用域的識別**，
   否則第 2 步收斂不出答案。
2. **服務裁決。** N 個宿主同時提案，收斂成**一個**答案。
   ⚠ 逐宿主 OR 是**單調沾黏**的：任何一條洩漏的提案把那一橫永久釘住，
   而那正是 S4。作用域對上才算，對不上一票都不投;還沒握手／還沒表明身分
   的連線一票都不投。
3. **系統打平手。** 誰是前景**由 OS 回答**，不接受宿主各自宣稱 —— 兩個宿主
   同時說「我是前景」就退化回第 2 步的 OR。OS 也是唯一**不依賴宿主活著、
   不依賴宿主誠實**的一方：被凍結的進程、來不及送 deactivation 就被砍掉的
   宿主，都靠這一層擋。

**⚠ 「答不出來」是第三種答案，不是「沒有人在用」**

前景這一刻回答不了問題時**維持現狀**。兩個原因，兩個都是使用者看得到的事：

* **OS 答不出前景**：UAC 提示、安全桌面、切換桌面的那一瞬。他只是被問了
  一次系統權限，那一橫不該開始倒數消失。
* **前景是輸入法自己的視窗**：設定視窗、系統匣選單、那一橫自己的彈出選單。
  它不是一個宿主，答不了「使用者在哪一個宿主裡打字」這個問題。
  ⚠ 這一格是 2026-08-14 實際踩到的：使用者從那一橫點「設定」→ 視窗開起來
  → 3000 毫秒後那一橫在他眼前消失。**四端都會踩到**，因為每一端的設定
  介面都跑在自己的進程裡，而它**不是**一個宿主。
  ⚠ 為什麼是「維持現狀」而不是「顯示」：他也可能是從系統匣／選單列
  （上面那條 ⚠ 要求的、與這一橫無關的入口）打開設定的。那時候那一橫本來
  就該藏著，強制顯示等於把 S4 換個地方放回去。

**為什麼是「有沒有人在用」而不是「有沒有在組字」：**

跟著組字走的話，使用者想切中英的那一刻這一橫**不在**（他還沒切，所以
還沒觸發顯示），而且每打一段就閃一次 —— 而中英切換正是這一橫存在的
理由（§12.10.2）。跟著「焦點那一條執行緒上是不是我們」走則與「哪一個
輸入框」無關：同一支程式裡跳輸入框不會觸發;而在都用本輸入法的程式之間
Alt+Tab 時，答案從一個 true 換成另一個 true，那一橫不閃。

**為什麼焦點是作用域，不是加強條件：**

輸入法在 Windows 上是 **per-thread** 的（系統設定裡「讓我為每個應用程式
視窗使用不同的輸入法」把這件事做成使用者看得見的事實）。也就是說
「這個輸入法有沒有被使用」這個問題**沒有全域的答案** —— 它只在
「哪一條執行緒」這個作用域裡才有答案。焦點不是拿來加強一個全域布林的，
它**就是**那個作用域。少了它，13 個宿主的答案會被 OR 成一個永遠是真的值。

**規範外的硬依據：**

Microsoft 對第三方 IME 的官方要求裡有一節叫 "Don't use sticky windows"，
原文明寫使用者不需要打字時 IME 視窗不該顯示。舊版的「一直都在」是那一節
的反例。這比「使用者覺得礙眼」有力，也是 §12.10.1 那一格改口的正當理由。

**放在哪裡實作：**

判準是**兩支**純函式，因為顯示時機的缺陷**全部長成時序問題**，而時序
問題沒有測試就只能靠人肉試 —— 人肉試不出「Alt+Tab 到另一個也用本輸入法
的程式時會不會閃一下」，更試不出「13 個宿主同時提案時誰贏」。

* `windows/common/bar_owner.{h,cc}` = 上面那三個層次的收斂（第 2 條的
  `in_use`、要回讀哪一個 session、以及「答不出來」）。
  `windows/tests/test_bar_owner.cc` 十三支，用的是使用者機器上的實際數字
  （13 個宿主、一個在前景），含 S4、UWP 的 `CoreWindow` 那一層、
  以及「前景是設定視窗」。
* `windows/common/bar_visibility.{h,cc}` = 遲滯。
  `windows/tests/test_bar_visibility.cc` 九支，含遲滯邊界
  （2999 / 3000）、恢復要取消而不是延後、以及「服務剛起來不可以先閃三秒」。

⚠ service 只負責接線，而**接線本身也要有守門**：判準有測試、訊號沒有，
是這個檔案反覆吃虧的形狀（`windows/audit_single_source.sh` 規則 6）。

#### 12.14.0 現況為什麼看起來像 Windows 95（逐條讀碼確認）

使用者的原話是「你這個設定感覺就是 win95 的方案」。那不是一個模糊的感覺，
下面五條各自對應畫面上的一塊，而**第 1 條一條就解釋了大半**。

##### 1. 沒有應用程式資訊清單 → 拿到的是 comctl32 **v5**

三種宣告方式各 grep 一次，`windows/` 底下全部 **0 命中**：

| 寫法 | 命中 |
|---|---|
| `*.manifest` 檔 | 0（`find windows/ -name '*.manifest'`） |
| `*.rc` 檔（可放 `RT_MANIFEST`） | 0 |
| `#pragma comment(linker, "/manifestdependency:…")` | 0（`grep -rn 'pragma comment' windows/`） |

MSVC 的連結器預設會產生一份 manifest，但**那一份不含**
`Microsoft.Windows.Common-Controls` 版本 `6.0.0.0` 的相依宣告。
沒有那一句，`InitCommonControlsEx`（`settings_window.cc:187`）啟動的
是系統目錄裡的 **v5**，而不是並列組件裡的 v6。

**後果是整個畫面：**

| 使用者看到的 | 誰畫的 |
|---|---|
| 立體的灰色按鈕（上移／下移／套用這個順序／關閉） | `user32` 的 v5 push button |
| 鑿進去的清單外框、方角、捲動會閃 | comctl32 v5 的 `SysListView32` |
| 沒有佈景的核取方塊與單選鈕 | 同上 |
| 灰底的捲軸滑塊 | v5 |

⚠ **這幾顆自繪修不掉**（§12.5.1 也不准為了好看自繪）。
v5 同時代表 `LVS_EX_DOUBLEBUFFER` 不存在（那是 v6 才有的擴充樣式），
所以清單捲動的閃爍也是同一個原因。

**規範性：Windows 端的可執行檔必須宣告 comctl32 6.0.0.0 的相依。**
三種寫法擇一即可，建議 `#pragma comment(linker, …)` 寫在
`windows/service/main.cc`，理由是它不需要把資源編譯器拉進建置
（§12.9.1 第 3 條已經為了同一個理由把 `.rc` 推遲過一次）。
新的 **W33** 在守這件事。

⚠ 這一條是從「檔案不存在 + MSVC 預設行為」推的，
**我沒有在真 Windows 上比對過 v5／v6 的截圖**。但它可證偽而且很便宜：
加上那一句、重建、開設定視窗，按鈕會從立體灰變成 Win11 的樣子。
如果沒變，這一條就是錯的，回來把它劃掉。

##### 2. 懸浮狀態列是方的，而且沒有陰影

`status_bar.cc::Paint()` 的順序是：

```
FillRect(client, kSurface)                       // ← 先把整塊填滿，含四個角
RoundRect(client, r, r) with NULL_BRUSH + pen    // ← 再畫一圈圓角外框
```

第二步只畫線，**沒有把四個角外面那塊底色挖掉**。
所以圓角是一條畫在方塊裡面的弧，視窗本身仍然是方的 —— 這正是
「方形、無圓角」。全檔 grep：`SetWindowRgn` 0、`CreateRoundRectRgn` 0、
`DwmSetWindowAttribute` 0、`CS_DROPSHADOW` 0。陰影不是「做得不明顯」，
是**沒有做**。做法見 §12.14.4。

##### 3. 「預設」徽章被切掉

`settings_window.cc:984` 把徽章的右緣釘在 `tr.right`，而
`tr.right = r.right − s4`，`r` 來自 `ui_listview.cc` 的 `RowRect()`。
那支在 `:77–84` 會把列寬**撐到 `GetClientRect` 的寬度**。

清單帶 `WS_BORDER` 而且**沒有** `LVS_NOSCROLL`（`settings_window.cc:94–97`），
所以項目一多就出現直捲軸；而欄寬是 `SyncRowListColumn` 在**上一次**擺位置時
用當時的 client 寬設下去的。捲軸出現之後 client 變窄、欄寬沒跟著變窄，
於是那一列比看得見的範圍寬，徽章被排到可視區外面，被 DC 的裁剪切掉。

⚠ **這一條的因果是我從碼推的，沒有在真 Windows 上重現過。**
不過修法與「因果對不對」無關：**徽章的位置不該從列矩形往回推**。
見 §12.14.6.5 —— 位置由純函式算，而且**明確扣掉捲軸寬**
（`GetSystemMetricsForDpi(SM_CXVSCROLL, dpi)`），這樣它在有沒有捲軸兩種
情況下都是對的，也才測得到。

##### 4. 四個文字盒比字矮（規範自己有那支函式，版面卻沒有用它）

| 側欄狀態一行（常數 20） | 20 | 16 | ✅ |
| 單選一列（`kMinTarget`） | 28 | 19 | ✅ |
| 按鈕（`kMinTarget + s2`） | 32 | 18 | ✅ |

`STATIC` 是 `SS_LEFT`（頂端對齊）並且會裁切，所以短的那幾格是
**每一個標題的下緣被削掉一條**。這與側欄那兩行被讀成「⼝以打字」
（`ui_layout.h` 檔頭記著的那次實機回報）是**同一族缺陷**，
只是這一次發生在右邊那一欄，而且四處都是。

**規範性：內容區每一個放文字的矩形，高度必須 ≥ `TextLineBoxDip(級距) × 行數`。**
新的 **W31** 是走過每一頁版面的單元測試，不是 grep。

##### 5. 懸浮狀態列的格子只有 26 DIP 高

`kBarH = 28`，而 `Relayout()` 把每一格上下各扣掉 `kBarBorder`(1)
→ 每一格 **26 DIP 高**，低於 §3.6 的 28 最小點擊目標。
W18 量的是設定視窗，量不到這一條。修法見 §12.14.7（整條改成 32）。

##### 6.（附帶）側欄選中時換字重，字會跳

`settings_window.cc:926` 是 `fonts_.Get(text_size::t3, selected)` ——
選中的那一項用 semibold。中文字型堆疊（`Microsoft JhengHei UI`）沒有 600，
GDI 會挑到 **700(Bold)**；而 Bold 的字比 Regular 寬，所以切頁時
側欄上那四行的寬度會**互相跳一下**。§12.14.3 規定選中不換字重。

#### 12.14.1 系統 accent color：怎麼拿、怎麼用、拿不到怎麼辦

##### 為什麼要跟系統

不是為了時髦。理由是 §12.7.3 已經記下的那個**做不到**：

> 核取方塊與單選鈕的**方塊本身**由 uxtheme 畫，`WM_CTLCOLOR*` 只影響文字與底。

也就是說：**畫面上一定會出現系統 accent 色的那一格，而我們改不掉它。**
其餘地方若堅持用青瓷綠 `#1F6F63`，結果是同一頁上兩個不相干的彩色
—— 而 §3.4 第 1 條寫的是「一頁最多一個彩色重點」。

跟著系統 accent，等於讓**唯一控制不了的那一格**與**其餘全部**講同一句話。
這也是 §9 那條規則的直接應用：「長得像該平台的原生控制項，
比長得像另外三端重要」。

⚠ **代價寫在這裡：**LuminaKey 的識別色在 Windows 上**不出現在設定介面裡**。
它仍然是安裝程式、圖示與另外三端的識別色。願意付這個代價的理由是
上一段；不願意的話唯一自洽的替代方案是**連核取方塊與單選鈕都自繪**，
而 §12.5.1 已經裁決過那件事（會拿走 MSAA 的角色與狀態）。

##### 取得（規範性，三段回落）

| # | 來源 | 取法 |
|---|---|---|
| 1 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Accent` → `AccentPalette` | `REG_BINARY`，32 位元組 = 8 組 RGBA。取 **index 4**（`AccentDark1`）給淺色、**index 1**（`AccentLight2`）給深色 |
| 2 | `HKCU\Software\Microsoft\Windows\DWM` → `AccentColor` | `REG_DWORD`，**`0x00BBGGRR`**（不是 RGB，位元組序相反）。拿到之後自己走下面的階梯公式 |
| 3 | 都讀不到 | **`#1F6F63`**（§3.4 的青瓷綠）當種子，走同一條階梯公式 |

⚠ **第 1 條的索引對照是公開流傳的知識，不是文件保證的。**
我沒有在任何一台 Windows 上 dump 過那 32 個位元組。
所以：**位元組數不是 32 就整段跳過，走第 2 條。**
索引若錯，錯的樣子是「顏色比系統的深一階或淺一階」，不是壞掉。

⚠ **不使用 `Windows.UI.ViewManagement.UISettings`**（WinRT）。
它是最準的來源，但會把 `combase.dll` 與 WinRT 啟動拉進一支
「必須讓外人用 `dumpbin /imports` 驗證它不連網」的程式（§12.1）。
兩個 `RegGetValueW` 換得到 95% 的正確性，那個交換划算。

##### 階梯（純函式，規範性）

只有種子色時，七階由這一組混色產生。混色是**每通道整數四捨五入**，
不是浮點 —— GDI 沒有 alpha，所有顏色最後都要是不透明值（§12.6 的同一個理由）。

```
mix(a, b, t) = round(a + (b − a) * t)     // 每通道

Light3 = mix(base, #FFFFFF, 0.70)
Light2 = mix(base, #FFFFFF, 0.50)
Light1 = mix(base, #FFFFFF, 0.30)
Base   = base
Dark1  = mix(base, #000000, 0.20)
Dark2  = mix(base, #000000, 0.40)
Dark3  = mix(base, #000000, 0.55)
```

##### ⚠ 對比守門（這一段是本節最重要的一條）

**系統 accent 是使用者選的，我們對它沒有任何保證。**
Windows 的 accent 挑色盤裡有 `#FFB900`（黃）與 `#00CC6A`（亮綠）——
它們當實心按鈕的底、上面配白字，是 **3.4:1** 與 **2.4:1**，
兩個都不到 WCAG AA 的 4.5。

所以 accent 進到色票之前要過三道，**每一道都是純函式，都測得到**：

1. **實心底上的字**：`#FFFFFF` 與 `#101010` 兩個候選，取對比高的那一個當
   `onPrimary`。（淺 accent 自動拿到近黑字 —— Win11 對亮 accent 就是這樣做的。）
2. **仍然不到 4.5** → 把底沿著「與字相反」的方向推（字是白就往黑推），
   用 8-bit 量化的二分搜尋找**第一個過門檻的值**。t = 1 是純黑／純白，
   一定過，所以這個搜尋不會失敗。
3. **accent 當文字或 1 DIP 指示條**時門檻不同：對 `surface` **與** `background`
   兩個底都要 ≥ 4.5（文字）／≥ 3.0（非文字）。
   ⚠ §3.4.1 記著一次「只驗一半就宣告過關」的事故（只算了對卡片、忘了對畫面底）
   —— 這裡兩個底都算，就是為了不再犯。

**hover／按下一律往「與字相反」的方向推 10%／18%。**
這保證按下去的對比**只會更高**。
⚠ Win11 自己是反過來的（accent 按鈕 hover 會變**淡**，用降透明度做）。
我們選相反的方向，理由只有一個：淡的那一版對比會掉，而我們沒有辦法
事先知道使用者的 accent 有多亮。**「按下去更沉」與「按下去更淡」

#### 12.14.3 字體與級距

##### 家族與回退鏈（現況已對，這裡只補「找不到會怎樣」）

`ui_font.cc` 的四條堆疊維持不變：

| 用途 | 順序 |
|---|---|
| 介面（拉丁） | `Segoe UI Variable Text` → `Segoe UI` → `Tahoma` → `MS Shell Dlg 2` → **空字串** |
| 正體中文 | `Microsoft JhengHei UI` → `Microsoft JhengHei` → `MingLiU` → 接拉丁那一條 |
| 簡體中文 | `Microsoft YaHei UI` → `Microsoft YaHei` → `SimSun` → 接拉丁那一條 |
| 等寬（診斷） | `Cascadia Mono` → `Consolas` → `Courier New` → **空字串** |

⚠ **CI 上跑的是 `windows-latest`，那是 Windows **Server**。**
`Segoe UI Variable` 隨 Windows 11 **用戶端**出貨，Server 映像上多半沒有；
`Microsoft JhengHei UI` 也要中文語言功能才在。也就是說：

> **CI 上截的圖，字體不是使用者會看到的那一套。**
> 拿 CI 的截圖判斷「好不好看」是無效的。視覺驗收只有真的 Win11 用戶端算數。

這一條寫在這裡是因為它會被踩：截圖全綠、真機難看，而沒有人知道為什麼。
`FontExists`（`EnumFontFamiliesExW`）保證退化路徑是對的，
所以 CI **不會壞**，只是**不代表**。

| token | 字級 DIP | `lfWeight` | 行高盒 DIP | 用在 |
|---|---|---|---|---|
| `t1` | 22 | **600** | **31** | 頁標題，一頁一個 |
| `t2` | 15 | **600** | **22** | 卡片／區段標題、對話框標題 |
| `t3` | 13 | **400** | **19** | 側欄項、清單列名稱、設定項的名字 |
| `t4` | 12 | **400** | **18** | 按鈕文字、狀態列每一格、現值 |
| `t5` | 11 | **400** | **16** | 白話說明、徽章、側欄底部兩行、視窗底部狀態行 |
| `t6` | 11 等寬 | **400** | **16** | 只有診斷 |

**行高盒 = `TextLineBoxDip(size) = size * 4 / 3 + 2`**（整數除法）。
「行高」在 Win32 上沒有別的意思：`DrawTextW` 不吃行距參數，
我們能決定的只有**配給那段文字的矩形有多高**。所以行高盒就是規範性的最小高度。
多行文字的盒高 = 行高盒 × 行數。§12.14.0 第 4 條列的四處違規就是對這張表量的。

⚠ **「行數」是版面的輸入，不是量出來的。**
版面必須為每一段說明**寫死**它佔幾行（現況的 `heading(head, blurb, N)` 已經是這樣），
因為 `LayoutSettingsPageDip()` 是純函式，它拿不到 HDC，量不了字。
代價是**換一個語系就可能折成不一樣的行數** —— 英文的說明通常比中文長。
所以：
1. 行數要按**最長的那個語系**寫（現況三語，取三者的最大值）。
2. 由此**「這一頁會不會出現捲軸」不是可以用眼睛決定的事**。
   `ScrollMaxDip()` 是純函式，把三個語系 × 四頁當測試案例跑，
   比在一台機器上開起來看可靠得多。
   ⚠ 反過來也成立：**在某一個語系下剛好放得下，不代表另外兩個放得下**，
   而放不下的後果不是難看，是最後一顆控制項碰不到。

##### ⚠ `lfWeight` 只准出現兩個值：`FW_NORMAL`(400) 與 `FW_SEMIBOLD`(600)

三條理由，缺一不可：

1. **500（§3.2 的 t3 Medium）在 Windows 上拿不到。**
   `Segoe UI Variable Text` 有 500，但 `Segoe UI`（CI 與 Win10 的退路）沒有；
   中文堆疊的 `Microsoft JhengHei UI` 只有 Light／Regular／Bold。
   GDI 的字型對映會挑最接近的一個，也就是 400。
   **所以 t3 直接寫 400**，層級改用**顏色**表達（`onSurface` vs `onSurfaceVariant`）
   —— §3.2 規則 1 本來就是「字級只表示層級，不表示重要性」。
2. **600 在中文下會落到 700。** 400 與 700 之間，600 離 700 比較近。
   所以 t1／t2 的中文標題實際上是 Bold。**接受它**，但正因如此，
   用 600 的地方要壓到最少（只有 t1 與 t2）。
3. **≥ 700 一律禁止。** 字體沒有粗體時 GDI 會**合成**粗體
   （把字形往旁邊多塗一次），在漢字上是一團糊。
   我們永遠不知道使用者機器上有沒有那個字重，所以永遠不要要求它。

⚠ **側欄選中項不換字重**（現況 `settings_window.cc:926` 有換）。
中文下那是 Regular ↔ Bold，字寬會變，四行的文字在切頁時互相跳。
選中由**底色 + 左緣指示條 + 文字色**表達，三個都是不會改變排版的訊號。

##### 其餘 `LOGFONTW` 欄位（規範性）

| 欄位 | 值 | 理由 |
|---|---|---|
| `lfHeight` | `-MulDiv(size_dip, dpi, 96)` | §12.3。負值 = 字元高度 |
| `lfQuality` | `CLEARTYPE_QUALITY` | 現況已對 |
| `lfCharSet` | `DEFAULT_CHARSET` | 現況已對 |
| `lfPitchAndFamily` | 等寬 `FIXED_PITCH \| FF_MODERN`；其餘 `VARIABLE_PITCH \| FF_SWISS` | 現況已對；家族名為空時 GDI 靠它挑 |
| `lfItalic` / `lfUnderline` / `lfStrikeOut` | **一律 0** | 斜體在漢字上是合成的（整個字形切變），永遠不要 |

#### 12.14.4 圓角、陰影、邊框

##### 圓角：Windows 端只有兩個值

| 級別 | 值 | 用在 |
|---|---|---|
| **視窗級** | **8 DIP** | 懸浮狀態列、方案彈出清單、確認對話框、候選窗 |
| **控制項級** | **4 DIP** | 卡片、側欄項、清單列、按鈕、輸入框、狀態列每一格 |
| 膠囊 | 高度 ÷ 2 | 只有「預設」徽章。它不是自由參數 |
| 焦點環 | 元件圓角 + 2（→ 6 或 10） | §3.6 |

⚠ **§3.3 的桌面欄（10／7／6／5）在 Windows 端不使用。**
理由是 §3.3 自己那一條：「按鈕的圓角跟平台走，不跟我們走」。
在 Win11 上，**所有**控制項的圓角都是平台給的，不只按鈕 ——
一個 7 DIP 圓角的清單列擺在 4 DIP 圓角的系統核取方塊旁邊，
看起來是兩套東西拼起來的。這是 §12.1 那條約束（系統控制項的外觀改不了）
往前推一步的結果，不是另一套審美。

⚠ **W3 的圓角允許集合因此改成 `{4, 8}`**（原本是 `{5,6,7,10}`）。見 §12.15。

##### 視窗級圓角怎麼做（規範性，兩條路，**不得同時用**）

```
1. DwmSetWindowAttribute(hwnd, 33 /*DWMWA_WINDOW_CORNER_PREFERENCE*/,
                         &pref, sizeof(DWORD))     pref = 2 /*DWMWCP_ROUND*/
   成功 → 完成。DWM 會做去鋸齒的圓角，而且陰影跟著對。
2. 失敗（Win10 沒有這個屬性）→
   SetWindowRgn(hwnd, CreateRoundRectRgn(0, 0, w + 1, h + 1, r, r), TRUE)
```

⚠ **`CreateRoundRectRgn` 的右下角是排他的**，所以是 `w + 1, h + 1`。
少了那個 +1，右邊與下面各少一像素，症狀是「外框在右下角斷掉」。

⚠ **兩條路同時走的結果是雙重圓角**（DWM 圓一次、region 再切一次），
邊緣會出現鋸齒的月牙。所以第 1 條成功時**不准**再呼叫 `SetWindowRgn`。
新的 **W29** 驗這件事。

⚠ **視窗級圓角只對 top-level 有效。** 卡片、清單列、按鈕是自己畫的矩形，
一律用 `RoundRect` 或 `CreateRoundRectRgn` + `FillRgn`，
**而且要記得把角外面那塊先填成底色** —— §12.14.0 第 2 條就是漏了這一步。

##### 陰影

| 表面 | 有沒有 | 怎麼做 |
|---|---|---|
| 懸浮狀態列 | **有** | `WNDCLASSEX.style \|= CS_DROPSHADOW` |
| 方案彈出清單 | **有** | 同上 |
| 確認對話框 | **有** | 同上（它是 top-level） |
| 設定視窗 | 系統給的 | 不管它 |
| **視窗裡的任何一塊**（卡片、清單、按鈕、徽章） | **沒有** | — |

**規範性：不得自己畫陰影。**
GDI 沒有模糊，自畫的陰影只能是幾條漸深的邊線 —— 那在 2026 年看起來
比沒有陰影更舊。`CS_DROPSHADOW` 是系統畫的，而且會**尊重使用者關掉陰影的設定**
（`SPI_GETDROPSHADOW`），那正是我們要的行為。

視窗裡不用陰影是 §3.5 第 3 條：「卡片與底只差一階，靠 1px 分隔線切開，
**不靠陰影**。深色下用陰影的結果是一坨黑。」

##### 邊框

| 用途 | 寬 | 色 |
|---|---|---|
| 分隔線（區塊之間、側欄與內容之間、底部固定列上方） | 1 DIP | `outline` |
| 卡片外框 | 1 DIP | `controlBorder` |
| 控制項外框（次要按鈕、輸入框、清單、狀態列） | 1 DIP | `controlBorder` |
| 危險按鈕外框 | 1 DIP | `error` |
| 主要按鈕外框 | **沒有** | 實心底自己就是邊界 |
| 焦點環 | 2 DIP 外 + 1 DIP 內 | `focusOuter` / `focusInner` |

⚠ **1 DIP 在 100% 下是 1 px，在 150% 下是 `MulDiv(1,144,96)` = 2 px**（§12.3）。
不要寫 `1`，要寫 `Dip(metric::kHairline, dpi)` —— 寫死的話高 DPI 下的線會太細到看不見。

#### 12.14.6 每一類控制項的自繪規格（四個狀態都給）

**讀法**：每張表的四欄是**一般／滑過／按下／停用**。
焦點是**疊上去的一層**，不是第五個狀態 —— 它可以與前四個任一個同時發生。
色值用 §12.14.2 的角色名，不寫 hex（換 accent 時 hex 會變，角色名不會）。

##### 12.14.6.1 側欄項（`SysListView32` + `NM_CUSTOMDRAW`）

幾何：寬 `200 − 2*s5` = 176，高 36，圓角 4，項與項之間 `s2`(4)。

| | 一般 | 滑過 | 按下 | 停用 |
|---|---|---|---|---|
| 底（未選中） | `background`（不畫） | `rowHover` | `rowPressed` | — |
| 底（選中） | `primaryContainer` | `primaryContainerHover` | `primaryContainerPressed` | — |
| 文字（未選中） | `onSurfaceVariant` | `onSurface` | `onSurface` | — |
| 文字（選中） | `onSurface` | `onSurface` | `onSurface` | — |
| 左緣指示條 | 選中才有 | 同 | 同 | — |
| 字級／字重 | t3 / **400（選中也是 400）** | 同 | 同 | — |

**左緣指示條**（Win11 NavigationView 的招牌）：
寬 **3**、高 **16**、垂直置中、**x = 項目的左緣**（不縮排）、圓角 2、
色 `accentIndicator`。
⚠ 它是「哪一頁」這個資訊的**第二個訊號**（第一個是底色）——
§3.4 第 2 條：不得只用顏色傳達資訊。指示條是形狀，色覺障礙下也在。

**文字左緣 = 項目左緣 + `s6`(16)**，**選中與未選中一樣**
（未選中時那 16 裡面是空的）。
⚠ 兩種狀態的文字左緣不一樣的話，切頁時四行字會左右跳 ——
與 §12.14.3 末段講的「換字重會讓字寬跳」是同一種缺陷的兩個來源。
16 剛好讓文字清開 3 DIP 的指示條還有 13 DIP 的餘裕，
而且它是 `space::s6`，不是一個新發明的數。

焦點：外圈 2 DIP `focusOuter`、內圈 1 DIP `focusInner`，圓角 6，
畫在項目矩形上，**不縮排** —— 縮排的話與底色圓角對不齊。

⚠ 側欄項**沒有停用態**。四頁都做得到就都在，做不到就整頁拿掉（§2-D1）。

⚠ **一頁最多一顆**（§3.4 第 1 條）。現況四頁裡只有「套用這個順序」與

⚠ **這一顆用系統控制項就會對** —— 前提是 §12.14.0 第 1 條的 manifest 補上，

也就是說：**「主要按鈕」= 給它 `BS_DEFPUSHBUTTON`，不要自繪。**

##### 12.14.6.4 危險按鈕（`BS_OWNERDRAW` + `WM_DRAWITEM`，自繪）

這是唯一自繪的按鈕，理由在 §12.5.3：啟用視覺樣式後 push button 不吃

| 高／圓角 | 32 / 4 | | | |

| 底（選中） | `primaryContainer` | `primaryContainerHover` | `primaryContainerPressed` | — |
| 名稱文字 | `onSurface` | `onSurface` | `onSurface` | `disabledText` |
| 字級／字重 | t3 / 400 | | | |

→ 名稱（t3，`DT_END_ELLIPSIS`）→ 彈性空白 → 徽章 → `s5`。

##### 「預設」徽章：長什麼樣、放哪裡

| 項目 | 值 |
|---|---|
| 形狀 | **膠囊**（圓角 = 高 ÷ 2 = 9） |
| 高 | 18（= t5 的行高盒 16 + 上下各 1） |
| 底 | `badgeFill` |
| 文字 | `onSurfaceVariant`，t5 / 400 |
| 左右內距 | `s3`(6) |
| 外框 | **無**（試算過 1 DIP 外框對徽章底只有 1.24:1，過不了 §3.4.1 的 1.4） |
| 垂直 | 在列裡置中（`(36 − 18) / 2 = 9`） |
| 水平 | **靠右**，右緣 = 文字欄的右緣 |

**⚠ 「文字欄的右緣」是這一格的全部重點，而現況算錯了（§12.14.0 第 3 條）。**
規範性的算式，寫成純函式放進 `windows/common/`：

```
scrollbar_w = list_has_vscroll ? GetSystemMetricsForDpi(SM_CXVSCROLL, dpi) : 0
text_col_right = list_x + list_w − border − scrollbar_w − s5
badge_right    = text_col_right
badge_left     = badge_right − (badge_text_w + 2 * s3)
name_right     = badge_left − s3            // 名稱截尾的右界
```

三件事同時被這個算式修好：
1. 徽章不再疊到捲軸上（**明確扣掉** `SM_CXVSCROLL`，而不是希望列矩形剛好對）。
2. 徽章不再被 DC 裁掉（它的右緣在可視區內，因為算式用的是控制項的寬度，
   不是列矩形的寬度）。
3. 名稱的截尾點與徽章的左緣**由同一個算式產生**，所以長方案名不會壓到徽章上。

⚠ `list_has_vscroll` 從哪裡來：`GetWindowLongW(list, GWL_STYLE) & WS_VSCROLL`。
**不要**用「項目數 > 可視列數」自己推 —— 那會在捲軸剛出現的那一幀算錯。

##### 每一格

| 格 | 內容 | 一般 | 滑過 | 按下 | 「停用」 |
|---|---|---|---|---|---|
| 1 `input_mode` | `中` 或 `En` | 底透明／字 `onSurfaceVariant` | 底 `rowHover`／字 `onSurface` | 底 `rowPressed`／字 `onSurface` | 不畫（見下） |
| 2 `variant` | `简` 或 `繁` | 同上 | 同上 | 同上 | 不畫 |

| 4 「設定」 | 在地化字串 | 同上 | 同上 | 同上 | 不畫 |

格的圓角 **4**（控制項級），底只在滑過／按下時才畫。

⚠ **第 3 格與第 4 格之間有一條 1 DIP `outline` 分隔線**，左右各 `s3`。
理由不是裝飾：1–3 格**改狀態**，第 4 格**開一個視窗**。
兩種不同的後果之間要有一個看得見的界線，否則使用者會以為第四格也是一個開關。
1–2–3 之間**沒有**分隔線（它們是同一種東西）。

⚠ **沒有焦點環。** 這一條是規格的一部分，不是漏寫：
懸浮狀態列是 `WS_EX_NOACTIVATE`（§12.10.3），它**永遠拿不到鍵盤焦點**，
所以焦點是一個不會發生的狀態。替它設計焦點環等於畫一個永遠不出現的東西，
然後在某一次重構裡因為「這段沒被走過」被刪掉，再被當成迴歸報回來。

⚠ 也因此**這一橫不是鍵盤可及的**。它承擔的功能（句中切中英）
在鍵盤上的家是別的地方 —— 那是 `product-gaps.md` §4.1.1 記著的那個洞，
**這一節不假裝補上它**。

| 步驟 | 規則 |
|---|---|
| 1 | 第 3 格的內容寬上限 **120 DIP**（含左右內距 → 格寬上限 140） |
| 2 | 超過就 `DT_END_ELLIPSIS`，在字元邊界截，**不在字元中間** |

| 4 | 壓到 120 還是超過 320 → 讓它超過。⚠ **不得**再往下壓：第 3 格是使用者辨認「現在是哪一種打字方式」的唯一依據，壓成兩個字等於沒有 |
| 5 | 擺位置時整條**必須完整落在工作區內**（§12.10.5 第 3 段的夾取，照舊） |

⚠ **截尾不得是死路。** 第 3 格點下去會開自繪的方案清單（§12.10.4），
清單裡是**完整的名字**，所以看不完的人有地方看。
這一條是 §2-D 的形狀：一個看不完的東西旁邊一定要有看得完的路。

|---|---|

| 整條 | 一句話，t4，`error` 色，水平置中，左右內距 `s5` |
| 外框 | 1 DIP `error` |
| 整條可點 | 是。點下去開設定視窗的「進階」頁 |
| 滑過／按下 | 整條 `rowHover` / `rowPressed`，圓角 8（跟著視窗圓角） |

### 12.16 §12.14 這一節裡哪些是讀碼確認的、哪些是我推的

**讀碼確認**（`main` @ `2bff4e0`，2026-08-10，逐條開檔看過或自己跑過 grep）：

* `windows/` 底下 `.manifest` 0 個、`.rc` 0 個、`#pragma comment` 0 處
  —— 三次 `find`／`grep` 各跑一次。
* `status_bar.cc::Paint()` 先 `FillRect` 再 `RoundRect(NULL_BRUSH)`，
  且全檔沒有 `SetWindowRgn`／`CreateRoundRectRgn`／`CS_DROPSHADOW`／
  `DwmSetWindowAttribute` —— grep，0 命中。
* 徽章的位置算式（`settings_window.cc:979–993`）與 `RowRect()` 的撐寬
  （`ui_listview.cc:77–84`），以及清單沒有 `LVS_NOSCROLL`（`:94–97`）。
* 側欄選中換字重（`settings_window.cc:926` 的 `fonts_.Get(t3, selected)`）。
* 狀態列每一格上下各扣 `kBarBorder` → 26 DIP（`status_bar.cc::Relayout()`）。
* 四個文字盒與 `TextLineBoxDip()` 的差 —— 兩邊都是 `ui_layout.cc` 裡的算式，
  在遠端跑 Python 各算一次。
* `ui_font.cc` 只用 `FW_NORMAL`／`FW_SEMIBOLD` 兩個字重（`:112`、`:122`）。
* §12.14.1／§12.14.2 的**每一個色值與每一個對比度**
  —— 在遠端跑 Python 算的，WCAG 2.1 相對亮度，八個 accent × 深淺兩份全跑過。

**我推的，沒有在真 Windows 上驗過（這一節同樣沒有任何一個字是在 Windows 上驗的）：**

1. **「沒有 manifest ⇒ 拿到 comctl32 v5 ⇒ 那些控制項長得像 Windows 95」**
   （§12.14.0 第 1 條）。從「檔案不存在」+「MSVC 預設 manifest 不含
   Common-Controls 相依」推的，符合公開文件與普遍作法，
   **我沒有比對過 v5／v6 的截圖**。
   ⚠ 這是本節最重要的一條，也是**最便宜可證偽**的一條：加上那一句、
   重建、開設定視窗看按鈕。沒變的話這一整段要劃掉。
2. **徽章被切掉的因果**（§12.14.0 第 3 條）。從欄寬與 client 寬的時序推的，
   **沒有重現過**。不過 §12.14.6.5 的修法不依賴這個因果成立。
3. **`AccentPalette` 的 32 位元組佈局與 index 1／4 的意義**（§12.14.1）。
   公開流傳的知識，**我沒有 dump 過那個登錄檔值**。
   規格因此寫了「位元組數不是 32 就整段跳過」——**那個退化路徑本身是規格的一部分**。
4. **淺色用 `Dark1`、深色用 `Light2`**（§12.14.2）。來自 WinUI 的
   `AccentFillColorDefaultBrush` 在兩個佈景下的定義，**我沒有讀過那份資源字典**。
   錯了的樣子是「顏色比系統的深/淺一階」，不是壞掉。
5. **`Segoe UI Variable` 不隨 Windows Server 出貨**（§12.14.3）。
   從「它是 Win11 用戶端的字體」推的，**我沒有在 `windows-latest` 的 runner 上
   列舉過字體**。⚠ 這一條若錯，結論反而更好（CI 的截圖更有代表性），
   所以它是安全方向的推測。
6. **GDI 在 600 與 400／700 之間會挑 700**（§12.14.3）。
   從「字型對映挑最接近的字重」推的，**沒有量過**。
   若實際挑的是 400，後果是中文標題不夠重 —— 那時把 t1／t2 改成 700
   仍然不行（會合成），正確的做法是改用**顏色與間距**做層級。
   規格已經往那個方向寫（t3 用 400 + 顏色分層），所以錯了也不必重寫。
7. **`CS_DROPSHADOW` 會尊重 `SPI_GETDROPSHADOW`**（§12.14.4）。
   已知的系統行為，**沒有實測**。
8. **卡片這個容器**（§12.14.5）。它是本節唯一一個**版面**上的改動，
   不是純粹的視覺參數。理由是「Win11 的設定介面每一個區塊都是卡片」，
   而那來自看過的畫面，不是量過的幾何 ——
   `product-gaps.md` §6 自承「我沒有量任何桌面端的幾何」，這一節同樣沒有。
9. **狀態列改成 32 高之後的觀感**。28 → 32 是為了讓格子滿足 §3.6 的 28，
   算式是對的，但**那一橫在螢幕上會不會變得太胖，我沒有看過**。
10. **§12.14.1 的整個裁決（Windows 端跟系統 accent、放棄青瓷綠）**
    是我做的判斷，不是使用者要求的細節。使用者的要求是
    「能對應 Windows 11 的系統 accent color」——
    **要不要因此讓識別色在 Windows 的設定介面裡完全消失，是一個產品決定，
    寫在這裡是為了讓它被看見、被推翻。**

**還有一件事這一節不回答：**這些規格**一行都還沒有實作**，
所以 §2-G1 對它自己成立 —— 在有人真的寫出 W29–W35 並實測會紅之前，
那張表的機器欄位都只是提案。
